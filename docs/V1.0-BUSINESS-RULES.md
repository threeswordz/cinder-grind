# V1.0 Production / Production Readiness — Business / Operational Rules

**Status:** APPROVED — Product / Business Owner, 2026-10-06 (Singapore time)  
**Issue:** #187

## Approved rules BR-V10-01–16

- **BR-V10-01 — No new business-function scope.** V1.0 hardens and operationalizes approved V0.1–V0.8 behavior; it does not silently add new ERP business policy.
- **BR-V10-02 — Exact-release deployment.** Production deploys an explicitly approved Git commit/release candidate, not an arbitrary working branch.
- **BR-V10-03 — Externalized secrets.** Production secrets/configuration are supplied outside Git and are not embedded in browser bundles.
- **BR-V10-04 — Forward migrations only.** Production schema changes use reviewed forward migrations; `prisma migrate reset`, ordinary `db push` and improvised destructive reverse SQL are prohibited.
- **BR-V10-05 — Backup before change.** Material Production deployments require an appropriate verified pre-deployment database/document backup or an explicitly documented equivalent recovery point.
- **BR-V10-06 — Database + Documents recovery consistency.** PostgreSQL metadata and document bytes are one logical business-record set for recovery planning.
- **BR-V10-07 — Compatibility-aware rollback.** Application rollback is allowed only when the prior application is compatible with the deployed schema; otherwise restore the matching database/storage recovery point.
- **BR-V10-08 — HTTPS Production boundary.** Authenticated Production browser/API traffic uses HTTPS.
- **BR-V10-09 — Browser-origin control.** Same-origin/same-site is preferred; separated browser deployments use explicit configured origins, never wildcard credentialed CORS.
- **BR-V10-10 — Session/CSRF security preserved.** Production hardening must not weaken approved server-side authentication, session invalidation, CSRF or authorization controls.
- **BR-V10-11 — Abuse controls are defensive, not authority.** Rate limiting protects abuse-sensitive endpoints but never substitutes for authentication/authorization. Production client attribution must not blindly trust spoofable forwarding headers; when a reverse proxy is used, the trusted proxy boundary must be explicit.
- **BR-V10-12 — Log minimization.** Operational logs must be useful for diagnosis while excluding credentials, token material, secrets and sensitive internal paths.
- **BR-V10-13 — Non-sensitive health.** Health/readiness endpoints expose only information needed for safe operation and do not leak secrets/business data.
- **BR-V10-14 — Production testing is non-destructive.** Production smoke checks use read-only or explicitly safe test operations; Production is not a general test environment.
- **BR-V10-15 — Open-source / zero-cost-first operations.** Baseline deployment, backup, logging, rate limiting and observability must have a fully open-source/self-hosted path; paid services require Change Control.
- **BR-V10-16 — Human go/no-go.** Technical green status does not self-authorize Production. Final readiness/Production go-no-go remains a Product / Business Owner decision.

## Approved owner decisions D10-01–12

| Decision | Proposed position |
| --- | --- |
| **D10-01 — Release purpose** | V1.0 is production-readiness/hardening over V0.1–V0.8, not a new business-feature release. |
| **D10-02 — Hosting commitment** | Keep deployment provider-neutral; final hosting/provider/cost commitment is a separate Product / Business Owner decision. |
| **D10-03 — Cost model** | DEC-008 remains mandatory; owned/self-hosted/open-source options are the default baseline. |
| **D10-04 — Production topology** | Preserve the modular monolith. A simple reverse-proxy → web/API → PostgreSQL + document-storage topology is sufficient baseline; no Kubernetes/microservices requirement. |
| **D10-05 — Secret/configuration model** | Environment/host-managed secrets and configuration are sufficient baseline; no hosted secret manager is mandatory. |
| **D10-06 — HTTPS / browser model** | HTTPS is mandatory for Production authenticated traffic; same-origin/same-site is preferred where practical. |
| **D10-07 — Recovery objectives** | Proposed baseline operational target: recovery point objective (RPO) no worse than 24 hours and recovery time objective (RTO) no worse than 8 hours for the initial deployment. Tighter objectives require separate approval/capacity design. |
| **D10-08 — Observability model** | Local/self-hosted structured logs + health/readiness + correlation IDs are sufficient baseline; no mandatory external APM/SIEM. |
| **D10-09 — Deployment automation** | Controlled repeatable deployment is required; fully automated continuous Production deployment is not required for initial V1.0. |
| **D10-10 — Identity/security scope** | Harden existing local/session identity and authorization. SSO/MFA/external IdP expansion is deferred unless separately approved. |
| **D10-11 — Performance policy** | Record representative benchmark/capacity evidence; do not invent a contractual performance SLA or concurrency commitment without owner approval. |
| **D10-12 — Release authority** | V1.0 technical readiness requires staging/rehearsal/recovery/security evidence; Product / Business Owner explicitly controls final readiness acceptance and any Production go-live authorization. |
