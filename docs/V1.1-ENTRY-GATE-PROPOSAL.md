## Purpose and authorization boundary

Design the next ERP stage around **eight real business personas and 54 workflow items** drawn from the bilingual 14-page Phase 2 PDF. Most V1.1 work should reuse V0.1–V1.0 approved code and business entities rather than silently create another system.

This document is a **decision package**, not a recorded approved scope or Change Control. A conversational "proceed" to prepare the plan does not waive the explicitly required V1.1 Product / Business Owner entry approval. **No V1.1-B+ runtime/schema/security changes, no merged successor roadmap amendment, and no V1.1 human acceptance are authorized by this draft.**

## 1. Proposed in-scope baseline

1. Eight configurable role experiences, no hard-coded named-user authority, no removal/rewriting of legacy employee/audit records.
2. Permission-aware application shell replacing 29-top-level-tab-first UI with grouped navigation, Home, My Work, project/company context and route/deep-link handling.
3. Canonical read-only workflow/task aggregation; no duplicate authoritatively mutable ledger, approval engine, stock ledger or Finance ledger.
4. Reuse of approved PR/RFQ/Supplier Quotation/PO/Goods Receipt/Supplier Invoice/Payment; Project/Budget/Site/Cost Control; Subcontracts/Claim/Certification/Finance handoff.
5. Existing-source action affordances and approval-queue routing, safe screen-level audit evidence and user-readable status/help.
6. th/en/zh-TW localization support for implemented V1.1 screens and role journeys. Preserve THB/backing currency semantics.
7. Evaluate K/T/H numbering support and preserve historical identifiers. **Changing transaction sequences requires explicit owner approval.**
8. Boundary validation for existing BOQ revision, GR, transfer, maker-checker and Subcontract VO workflows. **Policy changes remain approval-gated** and may be deferred if not decided.
9. Existing document attachment/traceability and print/export presentation only where already authorized by source module; no new mandatory paid dependencies.
10. Functional UAT and regression for eight personas + three canonical golden paths + Company/Project isolation.

## 2. Out of scope (hard deferral absent separate Change Control)

- Customer-facing Quotation AR creation/revision (#7); contractual interim customer progress billing (#13) and new billing inspection semantics (#14).
- New pre-order Work Request legal transaction (#19) beyond existing approved Work Order, new subcontract deductions (#22) and advance/deposit payment product (#24).
- Petty Cash / Worker Expense / reimbursement (#25–27).
- New stock status mutation, loss/writeoff, valuation or accounting cost-transfer transaction (#31–34) beyond already approved Inventory/Cost ledger rules.
- General/company-level non-project payments and receipts, cheques, bank transfer, vouchers and non-Project income (#38, #41–46) beyond existing V0.6.
- Statutory Thai tax invoice/VAT/WHT/GL/journals, chart of accounts (#40, #50–54).
- Fixed-asset accounting, depreciation, disposal (#47–49); new HR/attendance/payroll/social-security/tax/payslips.
- FX conversion, mixed-currency accounting, cross-project Supplier Invoices/Payments; production deployment by implication.
- AI, microservices, managed SaaS, mandatory paid libraries, new document storage service and UI-only security checks.

These are **discovered future requirements**, not V1.1 features.

## 4. Proposed acceptance criteria (not yet approved)

### A — Baseline
- **AC-V11-001**: Each of 54 PDF workflow items has stable ID, actor, disposition, evidence and required decision / delivery release; results are not misrepresented as full feature coverage.
- **AC-V11-002**: Eight persona-to-role-to-permission mapping preserves existing backend authorization.
- **AC-V11-003**: Proposed scope/exclusions, localization, supported Company context, stage boundaries and owner decisions are recorded and explicitly accepted in a Decision Log entry before implementation.
- **AC-V11-004**: Existing release evidence, immutable history and previously approved decisions remain intact.

### B — Role UX
- **AC-V11-005**: Home/My Work and grouped navigation appear based on effective permissions; no inaccessible module/task count appears.
- **AC-V11-006**: Role names/persons are configurable and not authority checks.
- **AC-V11-007**: Company / Project selection and route/drilldown preserve backend scope; direct API bypass fails.
- **AC-V11-008**: Navigation handles desktop/tablet/mobile and deep links without losing task context.
- **AC-V11-009**: Locale framework supports th/en/zh-TW without changing canonical statuses, money or stored business values.
- **AC-V11-010**: No mandatory paid runtime or unjustified additional infrastructure/dependency.

### C — End-to-end source journeys
- **AC-V11-011**: PR/RFQ/Quotation/PO/GR/Invoice/Payment tasks link to their canonical source records with typed statuses.
- **AC-V11-012**: Authenticated users can complete permitted transitions; maker/checker remains server-side.
- **AC-V11-013**: Subcontract claim/certification/retention and Finance references remain traceable without duplication.
- **AC-V11-014**: Project progress, Budget and Cost Control remain distinct source modules and preserve Original/Revision evidence.
- **AC-V11-015**: Rejection/return/exception actions exist in UI only where owning domain API and approved rule support them.
- **AC-V11-016**: Cross-company/project/budget/finance source drilldowns cannot disclose unauthorized details.

### D — Decisions and policy (gated)
- **AC-V11-017**: Pre-start BOQ editable-draft behavior protects immutable Original Budget and requires any owner-approved reapproval.
- **AC-V11-018**: GR maker/checker and discrepancy correction/resubmission cannot double-post stock or over-receive approved PO quantities.
- **AC-V11-019**: Any allowed self-approval exception is bounded, audited and post-reviewed exactly as explicitly owner-approved; otherwise normal maker/checker stays.
- **AC-V11-020**: K/T/H series changes retain all old business numbers/UUID links and are concurrency-safe.
- **AC-V11-021**: Subcontract VO-vs-new-SC conflict is decided and implemented only under explicit superseding Change Control; otherwise V0.5 SUB-009 remains authoritative.
- **AC-V11-022**: Cost/state/authorization/currency semantics remain unchanged absent approved decision.

### E — Evidence/exit
- **AC-V11-023**: Eight persona walkthroughs demonstrate scoped navigation, correct task ownership and rejection/unauthorized paths.
- **AC-V11-024**: Golden-path tests cover PR→P2P, Subcontract→Finance and Project→Cost/Management with evidence.

- **AC-V11-026**: Exact-head CI/PR CI and full applicable unit/API/browser/security regression pass.
- **AC-V11-027**: Fresh deployment/upgrade and forward-only migration checks pass as applicable; no V1.0 regression.
- **AC-V11-028**: Every stage's documentation/current-state handoff is reconciled after its merge/post-merge main CI.
- **AC-V11-029**: Product / Business Owner accepts V1.1 role/business UAT (human-only).
- **AC-V11-030**: Product / Business Owner explicitly authorizes V1.1 release closure (human-only).

## 6. Proposed data/API/security/test baseline

- **Frontend**: React + TypeScript + Vite + MUI + TanStack Query; reuse existing domain workspaces, add app-shell/navigation/locale abstraction. No hardcoded user IDs.
- **Backend**: NestJS modular monolith; existing canonical source endpoints and their existing permission/audit/idempotency checks; potential read-only Workbench API only after scoped design approval.
- **Database**: Prisma/PostgreSQL; **no schema migration in planning stage**. If later stage truly needs a new model, use only reviewed forward-only migration after approval and original-history guarantees.
- **Company and project**: never filter merely in UI; backend effective scope controls reads/mutations/counts and approvals.
- **Documents**: existing supported source associations; do not introduce alternative file store or unofficial statutory forms.
- **Tests**: eight role sessions; Company/Project boundaries; direct API permission denial; approval step eligibility; UI stale navigation; receipt rejections; finance idempotency; all current-release smoke suites.
- **Cost**: DEC-008 mandatory; no new paid/runtime dependency approved.
