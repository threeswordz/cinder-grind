## 1. Proposed in-scope baseline

1. Eight configurable role experiences derived automatically from the **signed-in user's administrator-assigned role(s)**. **No Switch Role UI or manual role toggling** (Product Owner-confirmed 17 October 2026); no hard-coded named-user authority and no removal/rewriting of legacy employee/audit records.
2. Permission-aware application shell replacing 29-top-level-tab-first UI with grouped navigation, Home, My Work, project/company context and route/deep-link handling.
3. Canonical read-only workflow/task aggregation; no duplicate authoritatively mutable ledger, approval engine, stock ledger or Finance ledger.
4. Reuse of approved PR/RFQ/Supplier Quotation/PO/Goods Receipt/Supplier Invoice/Payment; Project/Budget/Site/Cost Control; Subcontracts/Claim/Certification/Finance handoff.
5. Existing-source action affordances and approval-queue routing, safe screen-level audit evidence and user-readable status/help.
6. th/en/zh-TW localization support for implemented V1.1 screens and role journeys. Preserve THB/backing currency semantics.
7. Evaluate K/T/H numbering support and preserve historical identifiers. **Changing transaction sequences requires explicit owner approval.**
8. Boundary validation for existing BOQ revision, GR, transfer, maker-checker and Subcontract VO workflows. **Policy changes remain approval-gated** and may be deferred if not decided.
9. Existing document attachment/traceability and print/export presentation only where already authorized by source module; no new mandatory paid dependencies.
10. Functional UAT and regression for eight personas + three canonical golden paths + Company/Project isolation.
11. **Optional separately approval-gated proposal:** authorized read-only User Support & Diagnostics within Administration, using the administrator's *own* login to explain another user's account/permission/Project/approval blocker without impersonation or protected-source disclosure. Product Owner supported the concept on 2026-10-17; **new diagnostic permissions/APIs, retention, release inclusion and effort remain unapproved**. See dedicated proposal.
12. **Iterative UI direction confirmed 2026-10-17:** the reviewed English mockup is a **non-frozen visual direction**, not finished UI. Prefer small, modular shell/screen changes to enhance layout, navigation, cards, forms, mobile experience and localization throughout approved stages. Cosmetic/approved-workflow improvements use scoped tests and PRs; any new role/approval, Company/Project scope, stock, finance, security, migration or underlying business behavior still requires explicit authorization and Change Control. The detailed change-classification/feedback process is in `V1.1-UI-VISUAL-BASELINE-AND-REFINEMENT-PLAN-PROPOSAL.md`.

These are **discovered future requirements**, not V1.1 features.

## 6. Proposed data/API/security/test baseline

- **Frontend**: React + TypeScript + Vite + MUI + TanStack Query; reuse existing domain workspaces, add app-shell/navigation/locale abstraction. No hardcoded user IDs.
- **Backend**: NestJS modular monolith; existing canonical source endpoints and their existing permission/audit/idempotency checks; potential read-only Workbench API only after scoped design approval.
- **Database**: Prisma/PostgreSQL; **no schema migration in planning stage**. If later stage truly needs a new model, use only reviewed forward-only migration after approval and original-history guarantees.
- **Company and project**: never filter merely in UI; backend effective scope controls reads/mutations/counts and approvals.
- **Documents**: existing supported source associations; do not introduce alternative file store or unofficial statutory forms.
- **Tests**: eight separate users/sessions with administrator-assigned roles; login automatically shows effective authorized navigation/queues; **no role-selection control**; multi-role sessions cannot impersonate other users; role reassignment takes effect according to existing session invalidation/refresh rules; Company/Project boundaries; direct API permission denial; approval-step eligibility; UI stale navigation; receipt rejections; finance idempotency; all current-release smoke suites.
- **Cost**: DEC-008 mandatory; no new paid/runtime dependency approved.
