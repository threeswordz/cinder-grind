## Existing integration points verified

- `stock_transactions` stores signed DECIMAL(18,4) effects by Company, Warehouse, Material, nullable Project attribution and UOM, with immutable source, actor and timestamp evidence.
- Stage B receipt effects use positive `GOODS_RECEIPT` rows; full reversal appends exact negative `GOODS_RECEIPT_REVERSAL` rows. Both remain in the aggregate.
- The ledger already indexes `(company_id, warehouse_id, material_id, project_id)`; Stage C must use query plans compatible with that index and add only a justified source-controlled index.
- Warehouses retain optional fixed Project/Site context independently of per-transaction Project attribution. A general Warehouse can therefore expose separate Project-attributed stock groups.
- Effective Project access is database-derived through active User → Employee → Project Member, with `projects.access_all` as the only assignment bypass.
- Stage B currently exposes receipt-local movement history only; no Company stock balance endpoint or editable balance record exists.

## Implementation contract

1. Add explicit `inventory.stock.view` permission and secured read-only API/UI. Do not grant it automatically through technical `SYS_ADMIN`; Roles receive it through existing administration.
2. Derive each balance using PostgreSQL `SUM(stock_transactions.quantity)` grouped by Company, Warehouse, Material, Project attribution and UOM. Preserve DECIMAL(18,4) semantics and return quantities as decimal strings.
3. Return Warehouse code/name/site flag/active state and fixed Warehouse Project, transaction Project code/name, Material code/name and UOM code with the derived quantity. The read model has no identity or write path of its own.
4. Support bounded server-side filters for Project attribution, Warehouse, Material/search, active/archived Warehouse and zero-balance visibility. Default list shows non-zero balances; `includeZero=true` exposes net-zero historical groups without changing history.
5. Enforce Company and effective Project scope before aggregation. Assigned users see only rows attributed to their active assigned Projects. Nullable/unallocated Project stock is visible only with `projects.access_all`; a general Warehouse never broadens access to another Project's stock.
6. A requested inaccessible Project is denied/not discoverable consistently with existing Project access. Warehouse and Material filters cannot be used to infer hidden Project balances.
7. Project/Site view is a filter/presentation of the same aggregate, not a second stored balance. Archived Warehouses remain readable when included. Receipt reversal must net the original group to zero exactly.
8. Stage C introduces no reservation-based available quantity, negative-stock posting policy implementation, stock-changing action, movement-report export, valuation/cost column, cross-UOM aggregation or new source type.

## API and UI baseline

- `GET /api/v1/inventory/stock-projects`: effective active Project choices for balance filters.
- `GET /api/v1/inventory/stock-balances`: read-only aggregate with optional `projectId`, `warehouseId`, `materialId`, `search`, `includeInactiveWarehouses` and `includeZero`.
- Permission for both endpoints: `inventory.stock.view`.
- Inventory workspace adds a **Stock Balance** tab visible only with that permission.
- UI exposes Project, Warehouse/material search and archived/zero toggles, and clearly separates Warehouse fixed Project/Site context from transaction Project attribution.
- No Stage C mutation endpoint exists.
