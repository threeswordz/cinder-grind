# V1.0 Production / Production Readiness — Data / API / Security / Test Baseline

**Status:** APPROVED — Product / Business Owner, 2026-10-06 (Singapore time)  
**Issue:** #187

## 1. Data and migration baseline

- PostgreSQL remains the system of record.
- Prisma remains the approved application data/migration layer.
- Existing executed migrations are immutable.
- New migrations are forward-only and reviewed.
- Production uses `prisma migrate deploy` and verifies migration status.
- Production data is never reset as a normal deployment/recovery technique.
- A schema change must include rollback/recovery compatibility analysis.
- Database backups and Documents storage backups are linked as one logical recovery set.

No new database/business ledger is authorized merely for production readiness.

## 2. Documents storage baseline

The existing Documents storage abstraction remains authoritative.

Production readiness must provide:

- a writable configured storage root/provider path;
- path isolation from browser/API metadata;
- backup and restore procedure;
- access controls;
- upload limits and type/path protections;
- consistency verification after recovery.

No paid object-storage service is mandatory.

## 3. API / transport baseline

Existing `/api/v1` business contracts remain authoritative.

V1.0 may add only production-readiness support surfaces that do not redefine business semantics, for example:

- non-sensitive health/readiness status;
- correlation/request identifiers;
- operational metadata needed for safe deployment.

Production baseline:

- HTTPS;
- same-origin/same-site preferred;
- explicit CORS allow-list if origins differ;
- CSRF preserved;
- security headers;
- request-size controls;
- authentication rate limits with an explicit trusted-proxy/client-attribution strategy where applicable;
- controlled OpenAPI exposure;
- no secret-bearing error response.

Breaking business API changes require normal API versioning and Change Control; they are outside the default V1.0 hardening scope.

## 4. Security baseline

V1.0 must preserve and revalidate:

- backend authentication;
- hashed/protected credential/session material;
- server-side explicit permission checks;
- Company isolation;
- database-derived Project scope;
- `projects.access_all` assignment-filter-only semantics;
- technical SYS_ADMIN/business-authority separation;
- maker-checker where already approved;
- protected source-detail permission separation;
- audit immutability/history;
- CSRF;
- secure document authorization;
- no secrets in Git/frontend/logs;
- safe errors;
- request/file limits;
- dependency audit;
- rate-limit effectiveness across ordinary application restarts or at the approved reverse-proxy boundary;
- HTTPS Production transport.

No SSO/MFA/external IdP is implicitly authorized by this baseline.

## 5. Backup / recovery baseline

Proposed initial operating target:

- RPO: <= 24 hours;
- RTO: <= 8 hours.

Evidence must include:

- database backup command/process;
- document-storage backup process;
- recovery-set manifest/timestamp;
- restore drill;
- migration status after restore;
- authentication/read-only business smoke;
- document metadata/content consistency;
- recovery duration recorded.

The exact scheduling/storage mechanism may be selected technically if it remains open-source/zero-cost-first and does not create an unapproved recurring cost.

## 6. Observability / operations baseline

Required without mandatory SaaS:

- application/process logs;
- correlation/request ID;
- non-sensitive health/readiness;
- startup and migration failure visibility;
- local log retention/rotation;
- operations runbook;
- deployment/rollback/recovery evidence.

External APM/SIEM/log aggregation is optional only and requires normal dependency/cost review.

## 7. Performance / resilience baseline

V1.0 does not invent a contractual SLA.

Before exit:

- representative read-heavy Management/Project workflows are benchmarked;
- representative authenticated mutations are benchmarked;
- high-risk concurrency/idempotency tests continue to pass;
- no correctness/security regression is accepted for performance;
- material bottlenecks that make the intended initial Production use unsafe are blocking defects.

## 8. Automated technical gate

Each material V1.0 stage must retain applicable repository CI:

- dependency install with frozen lockfile;
- zero-cost UAT/environment validation where applicable;
- Prisma generate/schema validation;
- production dependency audit;
- migration-from-zero/status;
- API/web typecheck/test/build;
- prior-release regression;
- new V1.0 tests;
- authenticated live HTTP acceptance where applicable.

High-risk security, migration, concurrency, data-integrity or Production-runtime changes require DEC-022 stable-candidate Codex review unless an explicit PR-specific waiver is approved.

## 9. Release / readiness evidence

V1.0-E must prepare:

- exact release-candidate SHA;
- CI results;
- dependency audit;
- deployment rehearsal result;
- backup/restore rehearsal result;
- security hardening evidence;
- representative performance evidence;
- Production-safe smoke checklist;
- known defects/risk register;
- rollback/recovery readiness;
- Product / Business Owner readiness/UAT decision.

Automated evidence cannot self-complete AC-V10-039 or AC-V10-040.
