1. Keep V0.1–V1.0 functionality as canonical; implement an incremental, **modular and iteratively improvable** shell around existing React/NestJS modules instead of a rewrite; preserve the ability to revise screens per user feedback without altering approved business transactions.
2. User login automatically uses assigned `roleCodes` and *effective* `permissions` from `/auth/me`; one workspace, no role switcher, identity substitution or password sharing.
3. Permission-aware grouped left navigation; Home and My Work; Company and assigned-Project context; mobile-friendly Store Site/Foreman screens; Thai/English/Traditional Chinese **for the approved rollout surfaces**.
4. Role-specific drilldown and safe source-derived workflows for existing PR → RFQ/Supplier Quotations → PO → Goods Receipt → Supplier Invoice → Payment, plus Subcontracts and Project/Budget/Cost, without a new ledger, approval engine or stock-posting semantics.

6. Deliver tests, documentation, source links, scoped navigation and human UAT. Preserve DEC-008, DEC-016, DEC-022 and forward-only migrations.

**Deliberately exclude from the first implementation authorization:** all unapproved new business behavior, and the 25 PDF items classified Future/Not Evidenced (those classifications remain provisional). ## 6. Decisions needed specifically for optional diagnostics

A support administrator must **not** be able to bypass business source access merely because they can manage Users. For an approved diagnostics implementation, decide:
1. Which separate support-admin Role(s) receive a new proposed `admin.user_diagnostics.view` permission, and whether each access requires a case/purpose.
2. Same-Company user lookup only (recommended), role/permission summaries, and whether redacted eligibility explanations may reveal a transaction's existence (recommended NO absent source entitlement).
3. Diagnostic audit retention, correlation-ID search restrictions and operational log/identity linkage (existing path-only logging **does not** prove per-user events).
4. Delivery stage and cost re-estimate. Stage D is suggested only if the independent bounded security design is approved; otherwise defer.
