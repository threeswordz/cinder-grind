## 1. Objective

V1.0 makes the already-delivered V0.1–V0.8 Construction ERP safely deployable, recoverable, supportable and releasable to a Production environment.

V1.0 is a **production-readiness / hardening release**, not a new business-function release.

It must preserve:

- DEC-008 open-source / zero-cost-first;
- DEC-016 Chat / Work / GitHub operating model;
- DEC-022 Codex stable-merge-candidate policy;
- modular-monolith architecture;
- PostgreSQL + Prisma as the canonical relational/database-access foundation;
- existing Company/Project authorization, permission, audit and maker-checker boundaries;
- forward-only migration discipline;
- all approved V0.1–V0.8 business semantics.

## 2. In scope

### V1.0-A — Production Environment / Deployment Baseline

- define a portable Production environment contract;
- production-safe environment/configuration validation;
- external secret handling with no real secrets in Git;
- reproducible exact-commit build/deploy process;
- open-source HTTPS/reverse-proxy boundary;
- production-safe startup/shutdown/restart procedure;
- production deployment runbook and evidence format;
- same-origin/same-site deployment preferred where practical;
- hosting-provider-neutral deployment packaging.

### V1.0-B — Backup / Restore / Recovery

- PostgreSQL backup procedure;
- Documents storage backup procedure;
- database + file-store recovery consistency;
- backup manifest/evidence;
- restore drill in a non-Production environment;
- application rollback compatibility check;
- database/storage recovery procedure when schema/data rollback is required;
- documented baseline recovery objectives.

### V1.0-C — Security Hardening

- HTTPS-only Production transport;
- secure session/cookie configuration;
- CSRF enforcement validation;
- explicit CORS allow-listing;
- security headers;
- production-safe authentication-endpoint rate limiting, including trusted client attribution behind any reverse proxy;
- request-size / upload limits;
- production OpenAPI exposure policy;
- log/exception secret redaction;
- Production dependency/security audit;
- authorization/security regression across existing modules.

### V1.0-D — Operations / Observability / Performance Readiness

- non-sensitive health/readiness checks;
- correlation/request identifiers;
- structured operational logging suitable for local/self-hosted operation;
- log rotation/retention guidance;
- startup/migration failure visibility;
- operational runbook for restart, backup, restore and incident triage;
- representative performance/capacity benchmark;
- concurrency/idempotency regression on material financial/stock workflows;
- no mandatory paid monitoring/SIEM dependency.

### V1.0-E — Release Candidate / Deployment Rehearsal / Go-No-Go Evidence

- clean deployment rehearsal to a Production-like environment;
- migration-from-zero/status validation;
- upgrade-from-current-schema validation;
- backup/restore rehearsal;
- full applicable automated regression;
- authenticated live acceptance;
- non-destructive Production-safe smoke suite;
- release checklist / rollback readiness;
- Product / Business Owner readiness/UAT review;
- explicit Product / Business Owner V1.0 acceptance / Production go-no-go decision.

## 3. Explicit exclusions / deferrals

Unless approved by Change Control, V1.0 does **not** include:

- new Procurement, Inventory, Subcontracts, Finance, Cost Control or Management business capabilities;
- tax/VAT/statutory accounting, GL/journals/chart of accounts;
- FX conversion or mixed-currency consolidation;
- new payroll/HR functionality;
- microservices decomposition;
- Kubernetes;
- mandatory paid cloud hosting;
- mandatory managed PostgreSQL/object storage;
- mandatory paid identity provider/SSO;
- paid WAF/CDN;
- paid monitoring/APM/SIEM;
- multi-region active-active/high-availability architecture;
- dedicated data warehouse/OLAP/ETL;
- predictive/ML/AI business decisions;
- advanced report designer;
- mobile-native applications;
- external penetration-test vendor or formal SOC 2/ISO certification;
- a specific hosting/provider purchase commitment.

## 4. Production target boundary

V1.0 must remain portable.

The default proposal is **owned/self-hosted resources first where practical**, using open-source components. A specific Production hosting target, recurring paid service or cloud provider requires a separate explicit Product / Business Owner decision if it creates cost or provider lock-in.

V1.0 readiness work may be completed before a final hosting provider is selected, provided deployment artifacts/runbooks remain provider-neutral.
