**Document Status:** V0.1 Acceptance Criteria Baseline v0.1  
**Target Release:** V0.1 Foundation

**Requirements Baseline:** v0.1

---

# 1. Purpose

This document defines the objective pass/fail criteria for V0.1 Foundation.

V0.1 is accepted only when:

- all V0.1 Must Have requirements are implemented
- applicable acceptance criteria below pass
- critical automated tests pass
- UAT passes
- security and data-integrity gates pass
- no blocking defects remain

A working screen alone is not evidence of release acceptance.

---

# 2. Requirement Coverage

V0.1 contains:

- 64 total approved requirements
- 62 Must Have requirements
- 2 Should Have requirements

Should Have requirements:

- ADM-010 Audit Configuration
- ARCH-012 Podman Development Environment

A Should Have item may be deferred only when the deferral is documented and does not weaken a Must Have requirement.

---

# 3. Acceptance Status

Each criterion is marked during release validation as:

- Not Tested
- Pass
- Fail
- Accepted Exception

An Accepted Exception requires:

- documented reason
- risk assessment
- authorized acceptance
- follow-up issue where appropriate

Severity 1 defects cannot be accepted as exceptions for release.

# 4. Foundation and Authentication

## AC-V01-001 — Valid Authentication

Requirements:

FND-001, FND-012

Pass when:

- an active User with valid credentials can authenticate
- authentication does not require a paid hosted identity provider
- authenticated access is provided through the approved backend/session architecture

---

## AC-V01-002 — Invalid Authentication Rejected

Requirements:

FND-001, FND-007

Pass when:

- incorrect credentials do not create a valid session
- response does not disclose password/hash/internal authentication secrets
- repeated invalid requests are handled safely

---

## AC-V01-003 — Session Lifecycle

Requirements:

FND-002

Pass when:

- successful login creates a valid server-managed session
- authenticated requests work while session is valid
- logout revokes the current session
- expired/revoked sessions cannot access protected endpoints
- raw session secrets are not returned or logged

---

## AC-V01-004 — CSRF Protection

Requirements:

FND-002, FND-003, FND-012

Pass when:

- applicable cookie-authenticated state-changing requests require valid CSRF protection
- missing/invalid CSRF token is rejected
- valid CSRF token does not bypass normal permission checks

---

# 16. V0.1 End-to-End Acceptance Scenario

A release-candidate V0.1 environment must demonstrate:

1. Administrator creates/configures an active Project Manager User.
2. Administrator assigns appropriate Role/Permissions.
3. Customer, Employee, Material and UOM records are created.
4. Project Manager signs in.
5. Project Manager creates Project `PJ26001`.
6. Project references the Customer.
7. Project Team includes the linked Employee.
8. Project Manager creates hierarchical WBS:
   - 01 Groundworks
   - 01.01 Ground Floor Slab
9. Authorized user creates independent Cost Code `MAT-STEEL`.
10. Project Manager uploads a Project document.
11. Assigned Project user can view the Project/document.
12. Unassigned project-scoped user cannot access the Project/document.
13. Audit metadata/history is present for applicable actions.
14. Logout revokes the session.

This scenario must pass without any V0.2+ module being required.

# 17. Security Release Gate

V0.1 fails release acceptance if any of the following remains true:

- unauthorized user can access protected APIs
- project-scoped user can access unauthorized Project data
- System Administrator automatically gains business-approval authority
- audit history is normally editable
- raw password/session secrets appear in API responses or ordinary logs
- CSRF protection is absent from applicable cookie-authenticated mutations
- file path traversal is possible
- physical document storage path is exposed to unauthorized browser use
- secrets are committed to Git
- SQL/database errors leak sensitive infrastructure details to normal clients
