## UX product goal

Users should act on work assigned to them, not hunt across developer-named modules. **Product Owner-confirmed UI decision (17 Oct 2026): there is NO Switch Role section, impersonation picker or manual role toggle.** An administrator assigns role(s) to a user. On login, the authenticated session and `/auth/me` return that user's effective assigned `roleCodes` and `permissions`; the UI automatically renders the corresponding authorized workspace. When a person legitimately holds multiple assigned roles, the workspace combines only their effective authorized functions/tasks; it does not offer a role selector. Company/project access and each action/approval step are still checked on the backend.

## Common authenticated application shell (proposed)

Desktop: left grouped navigation with compact collapsed option; project/company context in header; content route and breadcrumb; bottom-right personal profile/settings and language selector. Small screens: drawer/mobile task cards, table-to-detail drilldown.

- **Home** — prioritized operational dashboard computed automatically for the signed-in user's assigned permissions and accessible tasks; no role selection.
- **My Work** — Drafts, Waiting for Me, Returned to Me, In Progress, Due Soon, Completed Recently.
- **Projects** — project workspace, team, BOQ/budget, scheduling, site execution, documents.
- **Commercial** — project variations, subcontracts, payment certifications, commercial cost controls.
- **Procurement** — PR, RFQ, vendor quotations/comparison, PO, delivery status.
- **Site & Inventory** — receipts, stock balance, reservations/issues/returns, transfers, equipment.
- **Finance** — supplier/client invoice, AP/AR, payments/allocations, retention and reports.
- **Reports** — already authorized operational / management read models.
- **Administration** — master data, employee/user/role management, approvals, number sequences, settings.

Never show inaccessible modules as empty cards. **Menu visibility is presentation only**; backend requires explicit action permission and effective project scope. Do not introduce a new universal `admin` or `management` bypass.

## Backend architecture for My Work (proposed, require design/approval)

A bounded read-only `Workbench` controller/service inside the **existing NestJS modular monolith**, e.g. `GET /api/v1/workbench/my-work?companyId=...&projectId=...`. First version could aggregate existing lists in the React client if fewer API changes are preferable; choose using performance/authorization evidence.

- Apply server Company isolation and `User → Employee → Project Member → Project` effective access.
- Apply action-level permission AND configured approval step to "Awaiting My Approval"; simply holding an `.approve` permission does not prove eligibility.
- Group canonical records only; no editable duplicate work-item database ledger; no second approvals engine.
- Return authoritative `sourceType`, `sourceId`, `sourcePath`, `state`, allowable actions and safe summary, or omit forbidden fields entirely.
- No unauthorized count leaks: dashboard and totals apply exactly the same filtering as detail endpoints.
- Idempotency and transaction checks stay inside owning module; UI optimistic actions cannot become settlement authority.
- Default polling/caching should reuse TanStack Query with query keys by company/project; do not add paid notification infrastructure.

## Golden paths and acceptance walkthroughs

### G1 — Procure to Pay (V1.1 highest priority)

`Store Site PR Draft → Khaimook Approval → Jai RFQ/Supplier Quotation/Selection → Jai PO Draft → Ben PO Approval → Store Site Goods Receipt Evidence → Jai Receipt Confirmation → Porn Supplier Invoice → Nancy Payment Approval → Settlement and project reporting`.

Verify every handoff with separate users; rejected/returned branches; direct API denial; correct source links and immutable approval history. Existing V0.6 rules enforce **single Project per Supplier Invoice and Payment**. Do not invent goods-receipt confirm/return transitions before the relevant owner decision.

### G2 — Subcontract to Finance

`Khaimook Work Request (proposed gap) → Jai Agreement/Order → Ben Approval → Subcontract Claim → Khaimook Work Acceptance → Assessment/Certification → Porn AP handoff → Nancy Payment`.

Use current **agreement, work order, claim, assessment, certification, retention, variation and allocation** models. Do not call a generic Work Order a separate approved Work Request until those semantics are approved. Keep retention withheld vs payable distinct.

### G3 — Project budget through reporting

`Nancy Project/Team → Ben BOQ Preparation → Nancy Budget Approval → Foreman Progress → Ben Review → Project Variation/Cost Control and Management dashboard`.

Preserve original-approved budget immutability and separate `Committed`, `Actual`, `Paid`, `Forecast`. Proposed construction-start lock may require new states/change control.

## Localization and documents

- UI locale `th`, `en`, `zh-TW`; localized navigation, validation/error mapping, date/amount display and status labels. Persist only canonical API values/statuses.
- THB should display as the currency for THB-backed records, **without overriding company currency code or inventing FX support**.
- Print/Export: define actual Thai/English/TW document templates later with Company legal names, historical numbers and current numbering rules; translated UI alone is insufficient.
- Favor existing React/MUI/TypeScript/TanStack Query; select open-source libraries only after license review under DEC-008.
- K/T/H names and historical document codes are independent of internal UUIDs.

## UX acceptance gates to propose (nonbinding)

- Each of eight role personas logs in and sees only authorized navigation and task counts.
- No role switcher exists; administrative role reassignment only affects the user through a refreshed authenticated session/authorization state. Where supported, changing permitted project context never leaks prior-project data; direct route/API denial works.
- G1/G2/G3 successful path + rejection/resubmission path tested with realistic approved scope.
- Mobile usability for Site Store/Foreman and desktop usability for Ben/Nancy/Jai/Porn.
- th/en/zh-TW text coverage validated with untranslated-key checks; money/currency semantics unchanged.
- Archived source documents / historical series and audit events remain traceable.
- Zero paid mandatory dependency added, no unauthorized schema migration, final release still requires human owner UAT.

## Design hold points

1. Is self-approval exception permissible (and exactly which audit/notification/review safeguards)?
2. Confirm Ben/Nancy monetary authority as **role-configured unlimited caps** vs approved system's current configurable approval policy.
3. Is Khaimook Site Store manager review needed on all transfers? Which transfer stages carry real stock postings?
4. GR mismatch, rejection and return-to-Store rules.
5. BOQ construction-start lock and allowed pre-start draft editing/reapproval.
6. Whether legacy added subcontract work uses new SC or approved VO behavior.
7. Whether customer progress billing, petty cash, GL/tax and HR/payroll remain out of V1.1 (recommended YES).

All remain **proposed** until Product / Business Owner approval and durable Change Control.
