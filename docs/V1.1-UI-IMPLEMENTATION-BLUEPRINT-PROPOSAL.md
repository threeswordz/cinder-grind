**Status: DRAFT / UNAPPROVED / DOCUMENTATION ONLY.** Issue #211 · Draft PR #212.
**Live reference baseline:** main `8d00f7f096fe42514a3aa2d90352a6bc609dd670` (CI #4252 green); existing PR proposal head originally `9ca5f1843e30214abdab32ebf6b1d703820f8546`.
**Product input:** 14-page `Construction_ERP_Business_Workflows_TH_EN.pdf` (54 functions and 8 current personas) plus user-reviewed **illustrative** UI concept of 17 October 2026.
**Purpose:** A safe, source-specific build plan for the proposed V1.1-B/C experience. This file authorizes **no application code changes** until a successor release entry package is explicitly approved and completed through GitHub release gates.

## 1. Implementation principle

**Incremental UX redesign, NOT a platform rewrite.**

- Retain React 19, Vite, TypeScript, Material UI 7, TanStack Query, NestJS, Prisma/PostgreSQL and the existing session/CSRF/RBAC model.
- Reuse canonical source modules and their approved state machines; build a navigation/workbench layer *around* them.
- Never introduce an alternative editable PR/PO/stock/invoice/payment/approval register for convenience.
- Avoid large replacements of existing panels; preserve working source CRUD/mutation routes while adding safe deep links.
- Keep backend-generated document IDs, company base currency, audit history and Project scope authoritative.
- Do not change `main` until exact-head CI, applicable review and post-merge requirements have been met.

## 2. Evidence-backed current UI starting point

- `apps/web/src/App.tsx`: `fetchCurrentUser()` read-only authenticated user; rendering `<AdminConsole user={authQuery.data}/>`.
- `apps/web/src/api/auth.ts`: `CurrentUser` includes `id`, `companyId`, `email`, `displayName`, `roleCodes`, `permissions`. **It does not include an authorized impersonation/role-switch API**.
- `apps/web/src/AdminConsole.tsx`: `sections` registry with `key`, `label`, `permission`, `content`; filtered via `user.permissions`; top horizontal MUI Tabs. The header still states `V0.8 Management` although V1.0 is accepted; treat as a presentation-only stale label.
- `apps/web/src/inventory/InventoryWorkspace.tsx`: second-level tabbed workspace with `GoodsReceiptsPanel`, `StockBalancePanel`, `StockTransfersPanel`, issues/returns/reservations.
- `apps/web/src/procurement/PurchaseRequestsPanel.tsx`, `PurchaseOrdersPanel.tsx` and sourcing: existing domain panels, approvals, scoped project options and query/mutation logic.
- `apps/web/src/finance/FinanceWorkspace.tsx` and Payment UI: preserve single-project Finance boundary, references and cancellation protections.
- No localization framework is currently declared in `apps/web/package.json`; localization can start with a typed internal dictionary before considering a new open-source dependency.
- `apps/web/src/admin/UsersPanel.tsx` manages users and assigned roles; `apps/web/src/admin/ApprovalPanel.tsx` manages approval steps. `apps/api/src/audit/audit.service.ts` records sanitized actor audit events. `apps/api/src/common/operational-log.ts` emits path/status/duration/correlation metadata **without proven user ID attribution**. There is **no verified unified user diagnostics UI**. See the optional standalone User Support proposal.

## 3. Correct interpretation of the sample UI picture

The sample image is **visual inspiration only**, not a source of business authority or evidence of actual pending task counts. The following image details **must NOT be copied into code**:

1. **REMOVE the sample's entire "Switch Role" section.** Product Owner confirmed (17 Oct 2026): administrators assign role(s) to each user; on login the authenticated session's `/auth/me` returns effective `roleCodes` and `permissions`. The workspace loads automatically from these backend-derived permissions, with **no manual role switch, impersonation panel or role filter**. If a user has multiple assigned roles, show their combined permitted tasks/sections while enforcing individual approval-step and Project/Company eligibility. Do not let a role label itself grant authorization.
2. **Correct personas:** Nancy = Accounting Manager; Ben = General Manager; Khaimook = Project Manager and Head of Store (assigned Projects only); Jai = Purchasing Staff; Store Site = Store Staff; Foreman = Site Foreman; Porn = Accounting Staff; Koh = HR Staff. Do not seed arbitrary mockup identities such as Somchai/Anong/David/Suda as authoritative user roles. Khae/Jasmine are removed only from *current responsibility assignments*, never historical audit data.
3. **PR approval belongs to Khaimook**, not Jai. **PO approval belongs to Ben**, not the person who prepared it. **GR receipt evidence belongs to Store Site**; **confirmation belongs to Jai**, after semantics are owner-approved. **Payment approval belongs to Nancy** where the configured approval step permits it.
4. Mockup sample quantities, PR numbers, dates, suppliers, project titles and currency amounts are fabricated preview data, not data loaded from the live backend.
5. No role-based page may offer an unauthorized action, even if a user can type the URL directly. Backend role/step/project checks remain mandatory.

## 4. Proposed UX navigation and component ownership

| Existing file / capability | Proposed *additive* change | Backward-compatibility rule |
|---|---|---|

| New `app-shell/AppShell.tsx` | Responsive drawer, app header, content region, mobile navigation | No business mutations or embedded access grants |
| New `app-shell/moduleRegistry.ts` | Single source list of group/key/route/required permission and lazy content | Do not silently replace current permission logic with weaker prefix matching |
| New `app-shell/Navigation.tsx` | Home/My Work and grouped Projects/Commercial/Procurement/Site/Finance/Reports/Admin | Hide unpermitted labels; server still guards all backing APIs |
| New `app-shell/UserContextBar.tsx` | Show logged-in name, assigned role label(s) as **read-only**, company, scoped project, locale, logout; **never render a role switcher** | Do not expose or impersonate other users; one authenticated company context unless backend supports more |
| New `app-shell/RouteAdapter.tsx` | Deep link to existing owning module and selected record | Preserve source component's own read/scoped fetch; unavailable/unauthorized record must fail closed |
| New `workbench/RoleHome.tsx` | Source-derived cards with counts only from authorized source lists | Loading/error/no permission must not reveal another project count |
| New `workbench/MyWork.tsx` | Queue filters (mine, waiting review, returned, completed) where the source API has eligibility evidence | Never infer actionable approval solely from a displayed name or role code |
| New `i18n/` | Typed `en`, `th`, `zh-TW` translations; presentational formatting | Canonical status, UUIDs, currency code, Decimal values remain unchanged |

| Proposed `admin/UserSupportDiagnosticsPanel.tsx` + limited read-only API, **only after separate security/scope approval** | Admin uses their own session to inspect safe same-Company assigned-role, Project and approval blockers for a named user | No role switcher, impersonation or business-record disclosure; explicit `admin.user_diagnostics.view`, every read audited, never infer user-specific logs without actual correlation evidence |

The exact file names are **proposed**. The approved implementer should verify repository convention, component naming and state handling before writes. No new API route is promised by this document.

## 5. Proposed vertical slices and safe cutover

### V1.1-B1 — Layout adapter (zero backend/schema change)

- Extract existing `sections` into a typed permission-preserving module registry with tests; retain old tab-panel contents without duplicating business logic.
- Implement responsive app shell, navigation groups, Home placeholder using **no fabricated business counts**; real safe user identity/header.
- Support existing module IDs as a compatibility landing mode so all V1.0 functions remain accessible.
- Fix the stale `V0.8 Management` UI header only as part of approved UI stage.
- Tests: module registry produces same or narrower visibility as legacy, authorization/direct API behavior unchanged, logout/session invalidation unaffected, mobile/desktop accessibility.

### V1.1-B2 — Authenticated workbench thin slice

- First real persona: **Jai (Purchasing Staff)**, but derive all menus, task counts and actions from the logged-in user's backend-effective **permissions and assigned approval steps**, not `displayName === 'Jai'` and not a manual role selection. Administrator-assigned role(s) are inherited on login.
- First real cards: *my Purchase Order drafts*, *RFQ/quotation comparison*, *receipt evidence needing confirmation only if backend supports/authorizes it*. Avoid "my PR approvals" for Jai.
- Start with existing safe `procurementApi` / sourcing / purchase-orders endpoints. If combining them causes significant overfetch/permission leaks, propose a bounded, permission-safe NestJS **read-only** summary endpoint under approved API design; no persistent work-item table.
- Tests: can view what owning API authorizes, cannot infer inaccessible counts, no direct mutation bypass, query cache scoped by `companyId/projectId`.

### V1.1-B3 — Project and locale context

- Add current company display, scoped project selector based on **backend returned accessible projects**, language toggle `en/th/zh-TW` and mobile drawer.
- When context changes, reset/query-invalidate appropriate cached lists and selected detail IDs; never leak stale cross-project data.
- Localize chrome and the first approved thin-slice screens; retain source server validation and date/number semantics.
- Tests: direct URL/project mismatch returns denial; locale switch does not resubmit requests or alter stored status; THB presentation uses true stored currency.

### V1.1-C1/C2/C3 — Canonical journeys, reused screens

- **C1 Procure to Pay:** Store Site PR creation → Khaimook PR approval → Jai RFQ/PO creation → Ben PO approval → Store Site receive evidence → Jai confirmation *only if source/approved rule supports it* → Porn AP prep → Nancy payment approval.
- **C2 Subcontract to Finance:** Agreement/WO → claim → scoped acceptance/certification → AP/Payment, retention safeguarded; do not automatically equate claimed with payable.
- **C3 Projects/BOQ to Reporting:** Project → budget (Original immutable) → Foreman progress → Cost and Management read-only views; user sees only authorized detail.
- Use route adapters to source modules; **no second backend state machine**. Any missing step is a proposed change-control item, not a silently enabled button.

### Optional support diagnostic slice — separately approval-gated

- Product Owner supported **User Support & Diagnostics** as a concept on 17 October 2026, not as permission to change auth/API or automatically include it in the release. Proposed detailed design: `V1.1-USER-SUPPORT-DIAGNOSTICS-PROPOSAL.md`.
- If explicitly authorized for this release, reserve an Administration navigation link for users with the *new approved* diagnostic read permission; reuse existing Users/Approval configuration and approved current Project-authority logic. Provide safe explanations; **no login-as-Chai, impersonation, source-detail entitlement, role escalation, approval action, session/token exposure or invented per-user request logs**.
- Approval needs a bounded endpoint contract, Company-target restrictions, diagnostic-read auditing, redaction/retention decisions, tests and a stable-green DEC-022 security review. Otherwise defer this entire slice rather than silently expanding V1.1-B/C.

### V1.1-D — Only expressly approved business refinements

- Treat BOQ pre-start lock, GR rejection/partial receipt, transfer acknowledgment, exceptional self-approval, K/T/H number changes and VO/new SC as separate owner decisions.
- **Safe default if undecided:** preserve V0.1–V1.0 rules, disable new exceptional actions and defer behavior changes. This is **not** a decision to implement a policy.
- Require stable-candidate DEC-022 independent Codex review for any auth, finance, approval, stock, data-integrity, concurrent numbering or migration change.

### V1.1-E — Evidence and owner UAT

- Exercise real separate users against PR/RFQ/PO/GR/AP/Payment; non-owned project denial; rejected/returned where supported; Subcontracts/Cost/reporting source links; three UI languages.
- Prove V0.1–V1.0 regression, exact-head/PR/post-merge CI and human-only acceptance. No claim that frontend screenshots alone prove business UAT.

## 6. Proposed UX safety gate / test matrix

| Scenario | Evidence required |
|---|---|
| Jai session vs Khaimook session | Different task lists; Jai cannot approve Khaimook PR without an actual independent configured approval role |
| Khaimook assigned Project A | Project B absent from lists/counts and denied on direct API/detail links |
| Store Site receiving | Draft/evidence allowed; confirmation/stock posting only as owning API/approved policy permits |
| Ben approves PO | Jai-authored PO approval permitted only for configured Ben step and within project scope |
| Porn prepares AP | Khaimook acceptance/certification link and allowed net amount; invalid unapproved source blocked |
| Nancy payment approval | Server-approved step, same-Project allocation target, idempotency and audit |
| Multi-role authenticated user | No role switcher or role filter; the same login automatically includes only the combined effective permissions/tasks from administrator-assigned roles, and never gains another user's identity, approval step or Project scope |
| Locale selection | en/th/zh-TW label change only; stored status/currency/UUID unchanged |
| Legacy document H identity | Historical number preserved; no renumber/migration side effects |
| Disabled/obsolete navigation | Old functional source workspace remains accessible until approved replacement passes CI/UAT |
| Optional User Support diagnostic | Admin can explain a configured blocker without seeing protected record details; an unauthorized admin gets denied, no user-identity substitution, and every diagnostic read is audited |
