## 1. Objective

Deliver auditable quantity-based Inventory control from approved Purchase Orders through receiving, storage, reservation, issue, return and transfer, with Project/Site attribution and derived balance/movement reporting.

## 2. Included requirements

| Requirement | Scope |
| --- | --- |

| INV-003 | Company Warehouse register with optional Project/Site context |
| INV-004 | immutable Stock Transaction Ledger for every posted physical movement |
| INV-005 | Stock Balance derived from the ledger |
| INV-006 / INV-007 | Project and Site stock attribution |
| INV-008 | Material Reservation without changing physical on-hand quantity |
| INV-009 | Material Issue |
| INV-010 | Material Return against a prior Issue |
| INV-011 | atomic Stock Transfer between Warehouses |
| INV-012 | historical Inventory transaction traceability |
| DOC-008 | Inventory transaction Documents through the existing secure Documents architecture |
| RPT-006 | Inventory balance and movement reporting |

## 4. Required architecture

- PostgreSQL/Prisma remains the business-data source of truth.
- physical stock changes only through atomically posted Inventory transactions.
- `stock_transactions` is immutable and append-only.
- Stock Balance and Inventory reporting are derived from source transactions; no editable balance table is permitted.
- Company and Project authorization remains server-side.
- the existing Approval Matrix, audit, numbering and secure Documents abstractions are reused.
- no new runtime dependency is proposed.
- DEC-008 open-source / zero-cost-first remains mandatory.

## 5. Proposed data baseline

The entry-gate data model is based on the existing ERD:

- `warehouses`
- `goods_receipts` / `goods_receipt_items`
- `stock_transactions`
- `material_reservations`
- `material_issues` / `material_issue_items`
- `material_returns` / `material_return_items`
- `stock_transfers` / `stock_transfer_items`

Posting metadata, approval/action history, reversal links, idempotency keys and stable source references may be added where required by the approved business rules. No migration or schema implementation begins before entry-gate approval.

## 6. Proposed API baseline

REST resources under `/api/v1/inventory`:

- Warehouses: list, create, update, archive/reactivate
- Goods Receipts: eligible PO lines, list/detail, create/update Draft, submit/approve/reject/post, reverse
- Stock: balance and immutable transaction history
- Reservations: list/detail, create, release, fulfill
- Material Issues: list/detail, create/update Draft, submit/approve/reject/post, reverse
- Material Returns: list/detail, create/update Draft, submit/approve/reject/post, reverse
- Stock Transfers: list/detail, create/update Draft, submit/approve/reject/post, reverse
- Reports: filterable balance and movement read models
- Documents: validated Inventory transaction target types through the existing Documents API

Exact paths and payloads are fixed during each stage pre-flight and must preserve this approved ownership/lifecycle baseline.

## 7. Test approach

Each stage must add:

- pure service/domain tests for quantity and lifecycle rules
- PostgreSQL integration tests for integrity, concurrency, atomic posting and immutable history
- API authorization tests for Company/Project scope and explicit permissions
- duplicate-request/idempotency tests for every stock-changing post
- live HTTP acceptance for the completed workflow
- V0.1–V0.3 regression and all prior V0.4-stage regression
- migration-from-zero, typecheck, production builds and dependency audit in CI

The V0.4 release walkthrough must cover PO receipt, partial/multiple receipt, balance derivation, reservation, issue, return, transfer, documents, reporting, traceability and unauthorized posting denial.

## 8. Excluded from V0.4

- inventory valuation methods, unit-cost layers and accounting journals
- Actual Cost, Committed Cost and Paid Cost ledgers
- Supplier Invoice, three-way matching and payment
- tax/VAT and multi-currency
- batch, serial, lot, expiry and quality-inspection workflows
- barcode/mobile-scanner integration
- inter-company stock transfer
- in-transit transfer workflow
- UOM conversion
- automatic reorder, purchase planning and demand forecasting
- manufacturing/BOM consumption
- negative stock
- editable Stock Balance
- paid or proprietary mandatory runtime services

Excluded items require later release scope or Change Control.
