## Existing integration points verified

- PO revision identity is `poNumber` plus `revisionNo`, with immutable prior revisions linked by `previousRevisionId`.
- PO line `quotationAwardId` is a stable source-demand reference across copied revisions; `purchaseRequestLineId` and `materialId` / `uomId` retain source traceability.
- PO approval state is held in `ApprovalInstance`, with cancellation on PO; eligible source is the current non-cancelled approved revision, not a Draft/Submitted/Rejected revision.
- The current PO cancel/revise/update/approve paths do not yet consult Goods Receipt history. Stage B must add checks and cover races.
- `ApprovalService.approve` owns its own transaction today; a receipt-specific final-post hook or compatible in-transaction approval path is required so final approval, posting, action history and audit cannot commit separately.
- `NumberSequenceService.next` allocates a Company-scoped number transactionally at creation. `GRNYYMM-###` / monthly reset must be validated and reused without changing the approved format.

## Implementation contract

1. Persist Goods Receipt header/items with Company, Project, Supplier, Warehouse, current PO revision, stable award/source-demand key, Material/UOM and source snapshots. Require positive DECIMAL(18,4) quantities. Reject services and mismatched Company/Project/Supplier/Material/UOM; Site Warehouse must match PO Project.
2. Draft edit, submit and approval/rejection are explicitly permissioned and audited. The creator cannot perform final approval. Final approval is the posting operation in one serializable database transaction; there is no separately successful approval without stock effects.
3. Record an immutable signed `stock_transactions` row per receipt item, with Company/Warehouse/Material/Project/UOM, source, actor and timestamps. Reversal appends the exact opposite effect and a stable link, never edits/deletes posted rows.
4. One stable idempotency key and a database-enforced uniqueness constraint per post/reversal source prevent retry or concurrency from producing duplicate stock effects. Lock stable PO source-demand keys in a deterministic order; compare sum of non-reversed posted receipt quantity against the current active approved PO quantity under the zero-tolerance rule.
5. Enforce receipt-aware PO cancellation, line reduction and approved revision transitions: no cancellation after an outstanding receipt; no approved quantity below cumulative outstanding receipt; a newer revision must not silently redirect a submitted receipt to a different source.
6. A Warehouse with ledger history cannot move Company/Project. Archive only when derived on-hand is zero and no active reservation; Stage B has no reservation table yet and must keep the later reservation guard explicit for Stage D. Historical archived Warehouse remains readable.
7. Expose secured Project-scoped eligible-PO, list/detail, create/update Draft, submit, approve/reject/post and reverse endpoints. No editable stock balance table or V0.4-C report/UI is introduced here.
