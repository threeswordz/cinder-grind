## 1. Mandatory authorization model

- apps/api/src/auth/auth.controller.ts exposes the authenticated user's companyId, roleCodes and effective permissions through /auth/me. No Switch Role or impersonation UI.
- apps/api/src/authorization/permission.guard.ts checks **every** required route permission; apps/api/src/authorization/project-scope.service.ts checks effective Project membership. projects.access_all bypasses Project membership filtering only, **not** approval rights.
- The owning transaction domain and configured approval step also check document state, role eligibility and maker/checker. **An approve permission alone does not prove that a given document is approvable by this user.**
- Named employees are examples from the Phase 2 PDF, never hard-coded authorization subjects. The role matrix below is a **suggestion to configure only after owner signoff**, not a claim that the configuration exists or should be automatically seeded.
- Multiple legitimate assigned roles produce only one combined authorized workspace; system administration cannot automatically approve procurement, stock or financial transactions.
