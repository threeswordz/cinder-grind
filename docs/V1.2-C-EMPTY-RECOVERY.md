## Actual architecture and capture sequence

`PrismaService` connects during API module initialization and disconnects during module destruction. The UAT web server serves static `apps/web/dist` files and has no database connection. There is no separate worker in the current UAT startup scripts. API stopping must finish before capture; browser closure alone does not stop Prisma. A crashed/orphaned API, another Node/Prisma script, SQL client or migration process can keep clients connected.

1. Arrange a short local maintenance window. Finish work in other chats/tools first. Do not run migrations, bootstrap, uploads, fixtures, full tests, `prepare-release.sh` or database inspection concurrently.
2. Create a plan while services are still available. Plan pins the exact source container ID, name, PostgreSQL17.11 image, loopback DB binding, database/user, retained candidate and the complete `.env` hash. It requires Company `V12UAT`, Project ID `e30da8b5-315c-4c0f-946b-da56086e646c` / code `V12-THB-001`, PostgreSQL read-only queries, zero LOCAL rows/files and container client versions17.11.
3. In the terminals that run API/web, use Ctrl+C and wait for the processes to exit. Keep the source PostgreSQL container running. **Do not use `deploy/uat/stop.sh`: it stops PostgreSQL.** Close SQL clients and other scripts cleanly; do not terminate other database backends to force a pass.
4. Capture within one hour of plan creation. The tool requires TCP `ECONNREFUSED` at127.0.0.1:3001 and zero other PostgreSQL client backends across the source cluster. An online API, timeout, changed config/candidate/container identity, clients, files, metadata or migration drift refuses. It never stops services or disconnects clients itself.
5. Capture uses source-container `pg_dump --serializable-deferrable` with read-only PGOPTIONS, no owner/privileges/tablespaces, then an actual Documents tar archive. Before/after database evidence must match, including schema, every public table, sequences and migration history. Schema fingerprints use ordered logical catalog definitions (relations, visible column order/types/defaults, constraints, indexes, routines, triggers, enums/domains, views and row policies), excluding object OIDs and dump emission order that legitimately change on restore. Sequence parameters/state are compared separately; no mismatched component is skipped. A post-capture identity/offline/client/empty check must also pass. This is an operator-maintained maintenance window with repeat checks, not a server-side connection fence: keep every other writer stopped throughout. PostgreSQL can still perform ordinary internal maintenance/statistics writes; `businessWrites: false` describes the adapter's business SQL, not a read-only filesystem/database server.
6. Restart API/web promptly, even if capture refuses/fails. Restore can run afterward; it does not open a source database connection. Never run a restore into retained UAT.
7. Restore verifies the set, creates a unique `erp-v12-restore-*` container with `--network=none`, no published port/host mount/existing volume and tmpfs PostgreSQL data. It checks exact container ID/ownership label/image/isolation and a fresh empty database before `pg_restore`. It extracts only the already-validated archive into a new private drill directory. It compares restored evidence and removes only the proven owned container. Source credentials and ambient PostgreSQL settings are not inherited by target commands.

The adapter refuses a nonempty restored LOCAL table even when archive checksums pass. If new uploads appear later, stop using this empty-only procedure; prepare a separately reviewed nonempty UAT capture path. Never delete/archive metadata or bytes to regain eligibility.

## Failure and retention

A refusal is BLOCKED, never acceptance. `CAPTURE_INCOMPLETE_KEEP_EVIDENCE` means retain the partial set and journal; no READY marker is left. An attempt receipt prevents silently overwriting/reusing an attempted plan. Investigate before a new plan/fresh directory. API/web restart remains required on failure; do not reset the database or run a preparation script.

Each restore has a new `drill-*` directory and `restore.json`, retaining exact generated container name/ID/token and cleanup result. Failure never reports PASS. If ownership/isolation changes or cleanup fails, the tool leaves that resource for inspection; do not run broad `podman rm`, volume pruning or cleanup against a guessed name. Successful target containers are removed; the backup, plan, source fingerprint, capture journal, empty drill Documents and restore receipts remain private. No artifact cleanup is automatic.
