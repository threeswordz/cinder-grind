# Construction ERP — V0.1 Deployment / Rollback / Smoke Procedure

**Release:** V0.1 Foundation  
**Applies to:** Staging/UAT and later approved Production deployment  
**Database:** PostgreSQL  
**Document storage:** configured local filesystem through the Documents storage abstraction

## 1. Preconditions

The target environment must provide:

- approved Node.js and pnpm versions from the repository/toolchain
- PostgreSQL reachable through DATABASE_URL
- writable STORAGE_ROOT
- environment secrets supplied outside Git
- WEB_ORIGIN, API host/port and session configuration
- document upload policy configuration where environment-specific policy is required
- a database backup mechanism appropriate to the target PostgreSQL deployment
- a backup/recovery method for the document storage directory

Do not use a developer .env file as a Production secret-management mechanism.

## 2. Pre-deployment backup

Before changing an existing environment:

1. record the currently deployed Git commit/release
2. create a consistent PostgreSQL backup
3. back up the document storage root
4. verify the backup artifacts are readable and access-controlled
5. record backup identifiers/timestamps in deployment evidence

Database metadata and document bytes form one logical business record set. Recovery planning must keep them consistent.

## 3. Deployment

From the approved release candidate:

1. check out the exact approved Git commit
2. install dependencies with the frozen lockfile
3. generate Prisma Client
4. validate the Prisma schema
5. run the production dependency audit
6. apply migrations using prisma migrate deploy
7. verify prisma migrate status reports up to date
8. build API and web workspaces
9. start/restart the API/web application using the target environment's approved process
10. verify application/health logs contain no startup or migration failure

Do not use prisma migrate reset against Staging/UAT data that must be retained or against Production.

## 4. Staging/UAT smoke test

- application/web shell loads
- health endpoint succeeds
- valid user login succeeds
- authenticated current-user API succeeds
- Project list loads according to user scope
- WBS & Cost Codes workspace loads
- Documents workspace loads
- one safe Staging/UAT Project create/read flow succeeds
- one Project document upload/list/download flow succeeds
- unassigned Project access is rejected
- logout revokes the session
- server logs show no unexpected errors
- physical storage paths are not exposed in browser/API document metadata

Use dedicated Staging/UAT data. Do not perform destructive smoke transactions against Production.

## 5. Deployment failure

If migration or application startup fails:

1. stop the rollout
2. do not continue applying ad-hoc database changes
3. capture logs and the exact failing step
4. determine whether failure occurred before or after a migration committed
5. use the recovery path below based on data/schema state
6. retest in a non-production environment before another rollout

## 6. Application rollback

If the database schema remains compatible with the previous application version:

1. stop the new application version
2. redeploy the previously recorded known-good Git commit/build
3. restart services
4. execute safe smoke checks
5. verify logs and document access

Never assume application rollback is safe after a schema change without checking compatibility.

## 7. Database/storage recovery

Prisma migrations are treated as forward migration history. Do not improvise destructive reverse SQL in Production.

1. take the affected application offline or otherwise prevent writes
2. preserve the failed-state database/storage for investigation
3. restore the verified pre-deployment PostgreSQL backup
4. restore the matching document-storage backup
5. redeploy the application version matching the restored schema/data
6. run migration status and safe smoke checks
7. confirm document metadata and file bytes are consistent

## 8. Post-deployment evidence

Record deployed commit, deployment date/time, operator, PostgreSQL migration status, smoke-test result, defects, rollback/recovery action if used, UAT environment identifier and UAT evidence/sign-off reference.

## 9. Production boundary

V0.1 does not select or mandate a Production hosting provider. The architecture remains portable PostgreSQL + Node.js + configured document storage. Production deployment occurs only after the release/UAT gates and an approved operational target exist.
