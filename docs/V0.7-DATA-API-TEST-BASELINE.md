# V0.7 Cost Control — Data / API / Security / Test Baseline

**Status:** APPROVED BY PRODUCT / BUSINESS OWNER — 2026-10-03  
**Entry Gate Issue:** #137

## 1. Canonical measure mapping

| Measure | Canonical source | Recognition / timing |
| --- | --- | --- |
| Original Budget | first approved V0.3 BudgetRevision + lines | first final approval; immutable |
| Revised Budget | current/highest approved V0.3 BudgetRevision + lines | latest approved revision |
| PO Committed Cost | current applicable approved/non-cancelled PO revision lines | final PO approval |
| Subcontract Committed Cost | approved Agreement original value + approved non-reversed subcontract Variation deltas | current authorized ceiling |
| Work Orders | approved Subcontract Work Orders | allocation of subcontract ceiling, not extra commitment |
| Supplier Actual Cost | final-approved SupplierInvoiceItem amount | invoiceDate under D07-08 |
| Subcontract Actual Cost | approved non-reversed SubcontractCertification.certifiedGross | approvedAt under D07-08 |
| Inventory Actual Cost | none | GR/Stock/Issue are quantity evidence only |
| Direct Actual Cost | approved V0.7 Direct Cost Posting | postingDate |
| Paid Cost | approved/non-cancelled OUTBOUND Finance allocations to eligible cost targets | Payment date |
| Project Cash Flow | V0.6 full approved/non-cancelled Payment amount | D06-19; separate from Paid Cost |
| Remaining Commitment | derived per commitment source | current commitment less attributable recognized Actual, floored at zero |
| Uncommitted ETC | latest final-approved V0.7 Forecast line | forecast version |
| Cost to Complete | Remaining Commitment + Uncommitted ETC | derived |
| Forecast Cost | Actual Cost + Cost to Complete | derived |
| Variance | Revised Budget − Forecast Cost | derived |
| Original Contract Value | Project.contractValue | Project source |
| Revised Contract Value | Original Contract + approved non-reversed Project Variation deltas | derived |
| Actual Revenue | final-approved Client Invoice totals | invoiceDate |
| Cash Received | approved/non-cancelled INBOUND Payments | Payment date |
| Forecast Revenue | Revised Contract Value | derived |
| Forecast Profit | Forecast Revenue − Forecast Cost | derived |
| Actual Profit | Actual Revenue − Actual Cost | derived |

## 2. Persisted V0.7 records

Only genuinely new canonical business records are persisted:

### direct_cost_postings
Minimum baseline:
- id, company_id, project_id
- wbs_id nullable
- cost_code_id required
- posting_date
- description/reference
- amount Decimal
- lifecycle/approval evidence
- linked reversal evidence
- actor/timestamps/idempotency evidence as required

### cost_forecasts
- id, company_id, project_id
- forecast_date, version_no
- description nullable
- approval/lifecycle evidence
- current Forecast is derived as highest-version final-approved Forecast

### cost_forecast_lines
- forecast_id, project_id
- wbs_id nullable, cost_code_id nullable
- **uncommitted_etc_amount** Decimal
- remarks nullable

The conceptual ERD field named forecast_cost_to_complete is refined to uncommitted ETC so Remaining Commitment is not accidentally entered and counted twice.

### project_variations
- id, company_id, project_id
- immutable variation number
- description/reason
- signed value_delta Decimal
- approval/lifecycle evidence
- linked compensating reversal evidence

## 3. Records that must NOT be added

Do not create an editable cost ledger, editable Project cost total table, editable Budget copy, editable Committed/Actual/Paid balance table or report-owned financial source of truth.

Read models may be implemented as application queries or database views where useful, but they remain derived.

## 4. Financial precision

- PostgreSQL Decimal / Prisma Decimal is authoritative.
- Preserve source precision during calculation.
- Round only where an approved business rule requires it.
- UI JavaScript Number arithmetic must not determine stored/authoritative financial values.
- Base-currency-only under D07-09; no FX conversion or numeric reinterpretation.

## 5. API baseline

Primary read model:

- GET /api/v1/projects/{projectId}/cost-control
- optional controlled filters such as wbsId and costCodeId
- authorized source/drilldown surface for canonical evidence

Mutation families:

- /api/v1/cost-control/direct-cost-postings
- /api/v1/cost-control/forecasts
- /api/v1/cost-control/project-variations

Expected actions follow existing REST patterns: list/detail, Draft create/edit, submit, approve/reject, and controlled reversal where approved.

No frontend-only authorization is permitted.

## 6. Security baseline

- Company isolation always applies.
- Effective database-derived Project access always applies to Project-scoped reads/writes.
- Explicit cost.* permission is additionally required.
- projects.access_all bypasses Project assignment only and grants no Cost Control action/approval permission.
- SYS_ADMIN grants no implicit business approval authority.
- Aggregate reports must filter inaccessible Projects server-side before aggregation.
- Source drilldown requires matching source-module permission under D07-10.
- Cross-Company / cross-Project WBS or Cost Code references are rejected at service/database boundaries where practical.

Existing Cost Control permissions in ROLES-PERMISSIONS remain the permission catalogue baseline:
- cost.control.view
- cost.direct_posting.create / submit / approve
- cost.forecast.view / manage / approve
- cost.variation.view / create / submit / approve

Any additional permission requires explicit baseline amendment / Change Control.

## 7. Audit / concurrency / idempotency

- Material lifecycle actions are audited with actor/time/action/context.
- Approved V0.7 records are immutable through ordinary edit/delete flows.
- Correction uses linked reversal/replacement as approved.
- Sensitive create/action requests use stable replay/idempotency protection.
- Final approvals lock/recheck state and dimensional/source integrity atomically.
- Forecast approval must not result in multiple authoritative current Forecast versions for one Project.
- Concurrent Direct Cost or Project Variation actions cannot duplicate effects.

## 8. Testing baseline

Automated coverage must include:

- Original vs Revised Budget source tests;
- current PO revision and cancellation/supersession commitment tests;
- Subcontract agreement/Variation commitment without Work Order double count;
- Supplier Invoice Actual recognition;
- gross Certification Actual recognition and reversal handling;
- Goods Receipt/Inventory exclusion from Actual Cost;
- Direct Cost approval/reversal;
- Paid Cost settlement derivation distinct from Project Cash Flow;
- Committed/Actual/Paid separation;
- Remaining Commitment / Uncommitted ETC / CTC / Forecast / Variance formulas;
- Project Variation / Revised Contract / revenue/profit formulas;
- Project/WBS/Cost Code and Unallocated rollups;
- Decimal/rounding/precision coverage;
- cross-Company / cross-Project / missing cost.* / projects.access_all / SYS_ADMIN negative tests;
- aggregate leakage negative tests;
- source-drilldown permission tests;
- idempotency and concurrency tests for new mutations;
- migration-from-zero and migration status;
- full V0.1–V0.6 regression;
- API/web build/typecheck and dependency audit;
- authenticated live HTTP V0.7 acceptance.

Human V0.7 UAT and explicit Product / Business Owner release acceptance remain separate mandatory release-exit gates.
