## Data implementation contract

### Material Reservation

- `material_reservations` is one reserved Material/UOM quantity at one Warehouse and Project attribution, with optional WBS and Activity context, optional required date, `RSVYYMM-###` number, status and complete actor/time history.
- Lifecycle is Draft → Active → Fulfilled/Released/Cancelled. Only Draft data is editable. Terminal history is retained; no automatic expiry is introduced.
- Active quantity never writes a Stock Transaction. Available quantity is derived as on-hand minus Active Reservation quantity for the identical Company, Warehouse, Material, Project attribution and UOM dimensions.
- Activation locks the controlled stock dimensions, recalculates on-hand and active reserved quantity in the same serializable transaction, and rejects quantity above available stock.
- An Issue may link one Active Reservation line-context and must consume its full remaining quantity; final Issue posting changes it atomically to Fulfilled. Partial reservation fulfillment is not introduced because the approved lifecycle has no partial status and BR-V04-14 requires the linked Reservation quantity to be fulfilled.
- Release and cancellation retain history and release availability without changing the physical ledger. A Fulfilled Reservation is not silently reopened by Issue reversal; reversal preserves historical lifecycle and restores physical stock only.

### Material Issue

- `material_issues` is the Company/Project/Warehouse header with `MIYYMM-###`, issue date, optional issued-to Employee, Approval Instance, creator/submitter/poster/reverser, stable post/reversal keys, remarks, timestamps and reversal reason.
- `material_issue_items` stores line number, Material, positive DECIMAL(18,4) quantity, UOM, optional Reservation, WBS, Cost Code and Activity. Header/line dimensions must be same-Company and same-Project.
- Draft → Submitted → Approved/Rejected uses the configured `MATERIAL_ISSUE` Approval Matrix. Creator cannot perform final approval/posting.
- Final posting locks the Warehouse/Material/Project/UOM balance and relevant Active Reservations, recomputes on-hand and available quantity, rejects negative on-hand or use of quantity reserved by another reservation, fulfills a linked Reservation atomically, appends one exact negative `MATERIAL_ISSUE` ledger row per item and audits the action in one serializable transaction.
- Post/reversal keys plus source-item/movement uniqueness make retry and concurrency idempotent. Full reversal appends exact positive `MATERIAL_ISSUE_REVERSAL` rows. Issue reversal is blocked while any non-reversed Return remains against an Issue item so the approved return ceiling and physical quantity cannot be inverted.

### Material Return

- `material_returns` is the Company/Project/destination-Warehouse header with `MRTYYMM-###`, return date, Approval Instance, creator/submitter/poster/reverser, stable keys, remarks, timestamps and reversal reason.
- `material_return_items` references one prior posted Material Issue item and copies the original Material, UOM and Project traceability with a positive DECIMAL(18,4) return quantity.
- Draft → Submitted → Approved/Rejected uses the configured `MATERIAL_RETURN` Approval Matrix. Creator cannot perform final approval/posting.
- Final posting locks the source Issue lineage, derives cumulative non-reversed returns, rejects quantity above the issued quantity, validates the destination Warehouse/Project rule, appends one exact positive `MATERIAL_RETURN` ledger row per item and audits atomically.
- Full reversal appends exact negative `MATERIAL_RETURN_REVERSAL` rows. Because negative stock is prohibited, reversal revalidates and locks destination on-hand before posting.

### Shared immutable ledger

- Make receipt source foreign keys nullable and add nullable Issue and Return header/item foreign keys. Exactly one valid source-item family is present on every original ledger row; reversal rows additionally link through unique `reversal_of_id`.
- Retain signed DECIMAL(18,4), Company, Warehouse, Material, nullable Project, UOM, effect key, actor and timestamp. Add optional WBS, Cost Code and Activity attribution where the Issue context supplies them.
- Add database checks/partial unique indexes and source-validation triggers for original and reversal movement types. Existing receipt rows and guarantees remain valid through migration.
- No editable balance, availability cache, reservation ledger or second Stock Transaction table is permitted. Stage E later adds Transfer source links to this same ledger.

## API and permission baseline

All routes are under `/api/v1/inventory`, enforce authentication, explicit permission, Company/Project scope and CSRF on mutation.

| Resource | Read / Draft routes | Workflow routes | Explicit permissions |

| Reservations | list, detail, create, update Draft | activate, release, cancel | `inventory.reservation.view/create/edit/activate/release` |
| Material Issues | list, detail, create, update Draft | submit, approve/post, reject through Approval Matrix, reverse | `inventory.issue.view/create/edit/submit/approve/reverse` |

The Inventory workspace adds permission-gated Reservation, Issue and Return panels. UI visibility is convenience only; backend authorization remains decisive. `projects.access_all` bypasses Project assignment only and grants no Inventory action authority.

## Concurrency and integrity baseline

1. Use serializable transactions plus deterministic PostgreSQL advisory/row locks for Company/Warehouse/Material/Project/UOM controlled dimensions.
2. Activation, Issue posting, Return posting and stock-reducing reversal re-read ledger and Active Reservation totals after locks are held.
3. Concurrent reservations cannot reserve the same final available quantity twice.
4. Concurrent Issue posts cannot consume the same on-hand or Reservation twice.
5. Concurrent Returns cannot exceed the remaining returnable Issue quantity.
6. Idempotent retry returns the existing effect; a different source cannot reuse the same key.
7. Any failed state transition, approval, reservation fulfillment, audit event or ledger insert rolls back the entire action.
8. Database triggers continue to reject ledger UPDATE/DELETE and mismatched source dimensions independently of application code.
