## 1. Authority

V0.6-A is technically complete. This stage is governed by the approved V0.6 Finance baseline, DEC-008, DEC-016 and DEC-017 through DEC-021. No new business decision is introduced by this pre-flight.

## 2. Stage objective

Implement the Finance-owned Client Invoice lifecycle and derived AP/AR read models without introducing Payment/allocation mutation, progress billing, tax, FX, GL or Cost Control.

## 3. In scope

- Client Invoice header and generic line persistence.
- Exactly one same-Company Project and one valid same-Company Customer per Client Invoice.
- Immutable Company-scoped `CIYYMM-###` number.
- Company base currency only.
- Draft create/edit and retained line history.
- Submit/approve/reject through configured Approval Matrix with explicit permissions and maker-checker.
- Derived AR from approved Client Invoices less valid approved/cancel-safe inbound allocations when such allocation records exist.
- Derived AP from approved Supplier Invoices less valid approved/cancel-safe outbound allocations when such allocation records exist.
- AP/AR Company and effective Project authorization.
- Audit/history, replay protection, PostgreSQL integrity/concurrency, API/web flow, regression and live HTTP acceptance.

## 4. Acceptance / business-rule mapping

Primary: AC-V06-007–012 and AC-V06-032–036 where applicable.

Primary rules: BR-V06-07, BR-V06-10, BR-V06-16–20.

Approved decisions retained:
- D06-02: base currency only; no FX.
- D06-04: generic Project/Customer Client Invoice lines; detailed progress billing deferred.
- D06-10: no tax/VAT engine.
- D06-11: only final approved/non-cancelled sources contribute operational balances.
- D06-13: approved invoices immutable; no silent credit/debit/cancel model.

## 5. Data design

Extend the existing Finance module using the approved logical entities:
- `client_invoices`
- `client_invoice_items`

Use UUID identity, Company ownership, required Project and Customer, DECIMAL money, retained workflow/audit identity, replay keys/fingerprints, and forward-only migration.

AP/AR are derived read models. Do **not** add editable AP/AR balance tables or a second ledger.

## 6. API / authorization design

Follow the existing V0.6-A Finance resource conventions for Client Invoice:
- effective Project choices;
- workflow options;
- Project-scoped Client Invoice list/detail/create/edit;
- Draft line add/edit/remove;
- submit/approve/reject;
- derived AP/AR views.

Use explicit `finance.client_invoice.*`, `finance.ap.view`, and `finance.ar.view` permissions as applicable. `projects.access_all` changes Project assignment scope only and grants no Finance action authority. Technical SYS_ADMIN does not imply business approval authority.

## 7. Stage boundary

Explicitly excluded:
- detailed construction progress billing;
- Payment creation/edit/approval/cancel and allocation mutation (V0.6-C);
- subcontract Finance/retention handoff (V0.6-D);
- Project cash-flow and broader Finance reporting (V0.6-E);
- tax/VAT, FX/multi-currency, GL/journals/accruals;
- credit/debit notes and post-approval invoice cancellation;
- V0.7 Cost Control and V0.8 Management.

Stage B may read future-compatible allocation records for derived balances but must not implement Stage-C allocation mutation early.

## 9. Implementation / validation checkpoint

V0.6-B implementation is present on PR #122 and remains under final pre-merge validation. The implemented stage includes the Client Invoice lifecycle, derived AP/AR read models, Company/Project authorization, retained approval history, replay protection, PostgreSQL integrity/concurrency controls, Finance web flows and authenticated live HTTP acceptance within the approved Stage-B boundary.

Latest implemented hardening includes:
- approval actions cannot be re-parented into or out of Client Invoice approval evidence;
- competing direct decisions are serialized and duplicate actor decisions are rejected independently of APPROVE/REJECT value;
- retained Client Invoice actions require current-step workflow-role eligibility, action-specific Finance permission and effective Project access;
- final invoice actor/timestamps are bound to retained Approval Action evidence;
- multi-approver final-action identity is determined by `client_invoice_decision_order`, assigned only after the Approval Instance lock is acquired, rather than by `action_at` timestamp ordering;
- the internal BIGINT decision-order field is excluded from Client Invoice HTTP payloads so approval responses remain JSON-serializable;
- AP and AR balance selectors preserve effective Project scope while including archived Projects, so approved balances remain discoverable after archival;
- the Client Invoice viewer selector is also history-capable and includes archived scoped Projects, so Draft, Submitted and historical invoices remain discoverable to `finance.client_invoice.view` users even without AP/AR permissions;
- creation/setup remains active-only at the UI/service validation boundary: archived Projects are labelled, new Client Invoice setup options do not load, and new Draft creation is not offered for archived Projects;
- Client Invoice create/edit/submit/approve/reject permissions require `finance.client_invoice.view` when Role permissions are assigned, following the existing PO/Subcontracts discoverability pattern;
- direct forged actors/timestamps, unauthorized decisions, reassignment, duplicate/racing decisions and stale state transitions remain rejected;
- prior executed migrations remain immutable; all database hardening is forward-only.
