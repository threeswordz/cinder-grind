# V1.1 — Approved Business and UX Guardrail Rules

**STATUS: APPROVED ENTRY BASELINE — DEC-028 / Product Owner 2026-10-17.**
**Issue:** #211 · Entry PR #212 · 2026-10-17 Singapore · Baseline V1.0 COMPLETE + ACCEPTED.
These BR-V11-01–18 rules are **approved source-preservation guardrails** for the bounded V1.1 UI release. They neither override previous approved releases nor authorize additional domain/business transitions. Source precedence: `AGENTS.md`, approved Decision Log, V0.1–V1.0 scope/rules, then approved successor documents only.

| ID | Approved source-preserving business/UX guardrail |
|---|---|
| **BR-V11-01** | An authenticated user's assigned active Role(s) come from server identity and effective permissions on login. No UI manual role switch, identity substitution or user-specific approval hard-coding. |
| **BR-V11-02** | Role codes and UI menu visibility never independently authorize an action; explicit owning API permission + configured Approval Matrix eligibility + Company and effective Project scope + maker/checker govern. |
| **BR-V11-03** | A technical SYS_ADMIN may maintain administration only via its own permissions, not implicitly approve BOQ, PR, PO, Subcontract certification, Finance or stock. `projects.access_all` only bypasses Project assignment filtering. |
| **BR-V11-04** | A multi-role user sees the union of *their* legitimate effective permissions within each action/Project scope, not another person's role, identity, sessions or authority. |
| **BR-V11-05** | Navigation, Home, My Work, alert badges and dashboard counts expose only records visible under the same backend checks as source detail; empty/unknown states cannot reveal record existence or cross-Project totals. |
| **BR-V11-06** | UI task cards always link to canonical source record and current state; no shadow database of authoritatively editable tasks/approval statuses and no second stock/financial ledger. |
| **BR-V11-07** | Phase 2 owner mapping is a proposed Role configuration: Store Site PR prepare, Khaimook PR review/approve, Jai supplier sourcing/PO prepare, Ben PO approve where the actual configured step permits. Names are examples, not authorization checks. |
| **BR-V11-08** | Goods Receipt data/evidence remain source-owned; proposed Store Site/Jai separation cannot create a missing confirmation/return/partial receipt transition without owner-approved policy and concurrency tests. |
| **BR-V11-09** | V0.3/V0.7 approved first Original Budget and revision histories remain immutable; construction-start and pre-start edits require future separate approval. |
| **BR-V11-10** | V0.5 Subcontracts original commercial terms, VO-based change rules, claim/assessment/certification/retention-withholding and V0.6 Finance handoff remain canonical; no added new-contract substitute or direct unpaid retention release. |
| **BR-V11-11** | V0.6 Supplier Invoice/Payment each remain **single Project** (D06-17/D06-18). Payment amounts, allocation ceilings, settled balances and project cash-flow source treatment remain V0.6-derived, without FX/non-project bypass. |
| **BR-V11-12** | V0.4 Inventory Goods Receipt/posting, stock issue/return, atomic transfer and compensation/reversal rules remain unchanged; new inventory mutation/valuation is outside default V1.1. |
| **BR-V11-13** | The English/Thai illustrations are a **living visual design direction**, not mock business data or a frozen screen contract. Stage-scoped presentation/navigation/form changes remain editable but are documented, reviewed and tested. |
| **BR-V11-14** | English, Thai and Traditional Chinese are UI-facing text translations only. Canonical stored status/amount/IDs remain unchanged; show THB only for records with actual THB backing and do not imply FX conversion. |
| **BR-V11-15** | The owner-supported optional User Support concept never grants View-As, login-as-user, new approvals or source-record disclosure. A future diagnostic read permission and same-Company, redaction, audit/retention/security rules require separate explicit approval. |
| **BR-V11-16** | The 54-item workflow PDF is a requirements gap register, not blanket feature approval. All new quotation/progress billings, cash/advance/petty cash, tax/GL, assets, payroll and numbering/business-rule changes remain deferred without Change Control. |
| **BR-V11-17** | Reusable UI components cannot override source mutating APIs. Error, loading, rejected and returned states must match source state machines, and direct API permission checks must be tested independently of the navigation. |
| **BR-V11-18** | All future UI improvements use scoped GitHub branches/Issues/PRs; any business/security/architecture/permission changes first pass Product Owner Change Control; CI/review/post-merge gates and human UAT remain mandatory. |
