## Planned implementation boundaries

### E1 — Exact release-candidate identity and evidence
- designate one exact candidate SHA;
- require a clean exact checkout and green exact-head CI;
- record tool/runtime versions and the Production-like environment identifier;
- do not treat a moving branch name as release identity.

### E2 — Fresh and upgrade rehearsal
- preserve the current `fresh` empty-target guard;
- rehearse the full migration history from zero in isolated PostgreSQL;
- rehearse `upgrade` from the supported current pre-RC schema/data state with the target offline and a verified paired recovery point;
- verify Prisma migration status after both paths;
- use forward migrations only.

### E3 — Candidate runtime and smoke
- start the exact candidate in Production mode against the Production-like target;
- run authenticated live acceptance using isolated/non-Production data;
- run the canonical non-destructive HTTPS Production smoke after activation;
- capture deterministic evidence without exposing secrets, storage paths or credentials.

### E4 — Recovery and rollback readiness
- create/identify the matching paired database + Documents recovery point;
- complete isolated restore verification for the candidate;
- evaluate application-only rollback compatibility against the prior release;
- if migrations make application-only rollback unsafe, record restore of the matching recovery set as the rollback path.

### E5 — Release checklist and handoff
- consolidate exact SHA, CI, fresh/upgrade results, dependency audit, live acceptance, smoke, recovery/rollback evidence and known defects;
- stop at the Product / Business Owner gate;
- **do not mark AC-V10-039 or AC-V10-040 complete** without explicit owner action.

## Expected touch points

Expected, subject to implementation findings:
- a V1.0-E rehearsal/orchestration script under `deploy/` or `scripts/` that reuses existing Production/UAT/recovery commands;
- an isolated current-schema-to-RC upgrade fixture/rehearsal;
- a V1.0-E release-candidate checklist/evidence document;
- minimal CI wiring needed to prove the exact-RC technical gates;
- existing `deploy/production`, `deploy/recovery` and `deploy/uat` runbooks referenced rather than duplicated.

A schema migration is **not expected** for V1.0-E. No new runtime dependency is expected. If either becomes necessary, it must remain within the approved V1.0 technical scope, be forward-only where applicable, and receive normal review.

## Explicit exclusions

- no new ERP business feature or business policy;
- no Production deployment or go-live authorization;
- no self-completion of AC-V10-039/040;
- no destructive/reverse migration;
- no Production load/stress testing;
- no mutation of real Production business data for acceptance;
- no paid CI, APM, SIEM, deployment or recovery dependency;
- no hosting-provider commitment, Kubernetes or microservice redesign;
- no weakening of V1.0-A–D security, recovery, authorization or observability controls.
