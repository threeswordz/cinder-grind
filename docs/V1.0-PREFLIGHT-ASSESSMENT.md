# V1.0 Production Readiness — Pre-flight Gap Assessment

**Status:** ACCEPTED SUPPORTING EVIDENCE — Product / Business Owner, 2026-10-06  
**Issue:** #187  
**Draft PR:** #188  
**Assessed baseline:** main `452677c931cd0d7592f1135c6d9894f16113314a`  
**Purpose:** Distinguish production-readiness controls that already exist from controls that still require V1.0 hardening or operational packaging. This assessment does not authorize implementation and does not expand the proposed V1.0 scope.

## 1. Existing controls already present

The current V0.1–V0.8 codebase already contains several controls that V1.0 should preserve and verify rather than rebuild:

- PostgreSQL-backed health check at `GET /api/v1/health`.
- Database failure returns service-unavailable behavior from the health service.
- Correlation/request ID middleware is globally applied and returns `X-Correlation-ID`.
- Explicit configured CORS origin via `WEB_ORIGIN`; credentialed wildcard CORS is not used.
- Session cookies are `HttpOnly`, `SameSite=Lax`, and become `Secure` when `NODE_ENV=production`.
- CSRF guard exists for protected state-changing browser actions.
- Login rate limiting exists with configurable attempt/window values.
- Document upload policy already enforces configurable maximum file size, allowed MIME types, and unsafe filename/path rejection.
- Unexpected server responses are converted to controlled problem-details responses rather than returning raw stack traces to the client.
- API host/port, database URL, storage root, session lifetime, upload policy and login-rate limits are environment configurable.
- PostgreSQL development container binds to loopback only in the repository compose baseline.
- Existing CI already validates Prisma schema/migrations, production dependencies, workspace build/test and authenticated live acceptance.

## 2. V1.0-A — Environment / deployment gaps

Still required before Production readiness:

- no repository-owned Production deployment package/runbook is complete for reverse proxy + web/API process supervision;
- no approved Production HTTPS termination/reverse-proxy configuration is source controlled;
- Production environment validation should fail fast for unsafe/missing critical configuration rather than relying only on local-development defaults;
- `WEB_ORIGIN`, `API_HOST`, `NODE_ENV`, secret inputs and storage configuration need an explicit Production contract;
- secret injection/rotation procedure remains operationally undefined;
- process start/restart/shutdown/recovery procedure needs Production evidence;
- no provider-specific hosting commitment should be introduced by this work.

## 3. V1.0-B — Backup / recovery gaps

Material missing operational evidence:

- no repository-owned PostgreSQL backup command/runbook is yet validated as the Production baseline;
- no paired Documents storage backup/manifest procedure is yet validated;
- no automated or documented recovery-set manifest links database and document storage at one logical recovery point;
- no recorded restore drill exists against a Production-like environment;
- rollback compatibility checking is described in prior documentation but has not been exercised as V1.0 release evidence;
- proposed RPO <=24h / RTO <=8h remain owner-policy proposals under D10-07, not current guarantees.

## 4. V1.0-C — Security-hardening gaps

### Already present but needs Production verification

- secure cookie mode;
- CSRF;
- explicit CORS origin;
- login rate limiting;
- upload size/MIME/filename controls;
- authorization and Project-scope regression;
- controlled 5xx client responses.

### Still materially incomplete or needing hardening

- no explicit application security-header middleware/configuration is visible in the current API bootstrap;
- no source-controlled Production reverse-proxy security-header baseline exists;
- login rate limiting is currently process-local/in-memory and resets on process restart;
- login rate-limit keying currently uses the socket remote address; a reverse-proxy deployment must establish a safe trusted-proxy/client-IP strategy before relying on it for abuse control;
- request/body-size policy outside document upload is not explicitly governed by repository configuration;
- operational exception logs can contain stack traces; V1.0 must verify/redact secrets and sensitive values in logs;
- Production OpenAPI/interactive documentation is not currently part of the runtime dependency set, so V1.0 should confirm that no unintended public interactive API documentation is exposed rather than add one;
- no external SSO/MFA/IdP is required by the proposed V1.0 baseline.

## 5. V1.0-D — Operations / observability / performance gaps

### Existing foundation

- correlation IDs already exist;
- NestJS logging exists;
- DB health check exists;
- shutdown hooks are enabled.

### Remaining work

- split or explicitly define liveness versus readiness semantics if required for safe Production process supervision;
- decide whether document-storage availability is a required readiness dependency and test it without leaking paths;
- define structured/consistent operational log format suitable for self-hosted support;
- define log rotation/retention;
- define startup/migration/deployment failure triage;
- establish representative capacity/performance evidence;
- preserve existing concurrency/idempotency regression for high-risk business effects;
- no paid APM/SIEM is required.

## 6. V1.0-E — Release rehearsal gaps

Still required:

- exact release-candidate deployment rehearsal;
- upgrade-from-current-schema rehearsal;
- backup/restore rehearsal;
- Production-safe smoke checklist;
- rollback/recovery evidence;
- consolidated known-risk/defect register;
- Product / Business Owner readiness/UAT evidence;
- explicit Product / Business Owner go/no-go decision.

## 7. Scope check

This assessment finds **no need to add new ERP business functionality** to V1.0.

The proposed A–E decomposition remains appropriate:

1. Environment / Deployment
2. Backup / Restore / Recovery
3. Security Hardening
4. Operations / Observability / Performance
5. Release Candidate / Rehearsal / Go-No-Go

The current codebase is already materially ahead of a bare prototype in authentication, authorization, CSRF, correlation, health, upload controls and CI. V1.0 should therefore focus on **hardening, Production-safe configuration, operational evidence and recovery**, not replacing working controls.

## 8. Owner-decision items that remain genuinely policy-level

The following should remain explicit owner decisions rather than being silently chosen during implementation:

- D10-02 final hosting/provider/cost commitment;
- D10-07 RPO/RTO target;
- D10-10 whether SSO/MFA/external identity is deferred;
- D10-11 whether any contractual performance/SLA commitment is desired;
- D10-12 final Production go/no-go authority.

Those owner-policy proposals were approved as part of the complete V1.0 entry package on 2026-10-06 under DEC-026. V1.0-A remains blocked only on the remaining durable entry-closure gates.
