---

# 1. Purpose

This document freezes the exact scope of V0.1 Foundation.

V0.1 does **not** attempt to deliver the entire Construction ERP.

Its purpose is to create the secure, auditable and technically stable foundation required by every later release.

---

# 2. V0.1 Release Objective

V0.1 is successful when an authorized user can securely use the ERP to:

1. sign in and operate under configured Roles / Permissions
2. administer the basic system configuration
3. maintain shared Master Data
4. create and manage Projects
5. assign Project Members
6. build a hierarchical WBS
7. maintain independent Cost Codes
8. upload and access Project Documents through the secure storage abstraction
9. use stable internal IDs and configurable business numbering
10. generate auditable actions without requiring paid runtime software

V0.1 establishes the platform.

It does not yet provide the Gantt programme, Procurement, Inventory, Subcontracts, Finance or Cost Control business workflows.

# 3. Requirement Count

- **64 total approved requirements**
- **62 Must Have requirements**
- **2 Should Have requirements**

Must Have requirements form the release gate.

Should Have requirements may be deferred without blocking V0.1 only if the deferral is documented and does not weaken security, data integrity or a Must Have requirement.

# 5. Functional Scope

## 5.1 Authentication and Sessions

V0.1 includes:

- authenticated access
- secure session management
- logout / session revocation
- inactive-user protection
- backend-enforced authorization
- CSRF protection for applicable browser mutations
- no paid hosted identity provider

Password recovery / self-service reset is **not** part of the approved V0.1 scope.

It may be introduced later through Change Control if required.

---

## 5.2 Roles and Permissions

V0.1 includes:

- Users
- Roles
- Permission definitions
- User-to-Role assignment
- Role-to-Permission assignment
- project-scoped access
- all-project access permission
- approval framework
- maker-checker framework
- audit framework

System Administrator does not automatically receive commercial approval authority.

---

## 5.3 Administration

V0.1 includes:

- Company Settings
- User Management
- Role Configuration
- Permission Configuration
- Approval Matrix Configuration
- Status Configuration
- Number Sequence Configuration
- System Configuration
- basic Audit Configuration where completed

---

## 5.4 Master Data

V0.1 includes:

- Customers
- Suppliers
- Employees
- Materials
- Units of Measure

Master records support:

- create
- view
- edit
- search/filter where appropriate
- deactivate/archive
- audit metadata

Historically referenced records are not casually hard-deleted.

---

## 5.5 Projects

V0.1 includes:

- Project ID
- Project Code
- Project Name
- Customer
- Contract Value
- Project Location
- Project Description
- Project Team
- Project Contacts
- Planned Start
- Planned Completion
- Project Status

Actual Project start/completion dates remain V0.2 according to the Requirements Baseline.

---

## 5.6 WBS

V0.1 includes:

- hierarchical WBS
- unlimited logical depth rather than hardcoded fixed levels
- parent/child relationship
- WBS Code
- WBS Name
- WBS Description
- Project ownership
- WBS active/inactive status
- work-package indicator

A parent WBS must belong to the same Project as the child WBS.

---

## 5.7 Cost Codes

V0.1 includes:

- Cost Code register
- code
- name
- description
- category where used
- active/inactive status

Critical architecture rule:

**WBS and Cost Code are independent dimensions.**

V0.1 must not implement a mandatory WBS → Cost Code parent-child hierarchy.

---

## 5.8 Basic Documents

V0.1 includes:

- Document Types
- document metadata
- local prototype file storage
- storage abstraction
- secure upload
- secure download
- Project document association
- Project-scope authorization
- archive/deactivate behavior where applicable

The browser does not receive physical server filesystem paths.

Object storage is not required for V0.1.

# 6. Technical Scope

V0.1 uses:

- Node.js runtime
- TypeScript
- React
- Vite
- MUI Core
- TanStack Query
- React Hook Form
- Zod
- NestJS
- REST API
- PostgreSQL
- Prisma ORM
- local filesystem document storage
- Podman as preferred local container tooling
- Git / GitHub for development

pnpm is the proposed package manager for implementation, subject to the approved Dependency License Register.

The exact dependency versions are pinned when coding begins.

---

# 7. Security Scope

V0.1 must implement and test:

- secure password hashing
- secure server-managed sessions
- CSRF protection
- backend permission enforcement
- Project-scope authorization
- maker-checker framework
- validation
- safe error responses
- audit metadata
- immutable audit history through normal ERP permissions
- no secrets committed to Git
- restricted CORS
- safe file handling
- path-traversal protection
- controlled file-size/type policy
- session revocation
- inactive-user protection

Security controls cannot be deferred merely to make the prototype faster.

---

# 8. Data Scope

V0.1 creates the foundational PostgreSQL schema required for its release.

Only the tables/migrations necessary for V0.1 need to be physically implemented during V0.1.

The full Database Baseline v0.1 remains the forward architecture reference.

Do not create unused future-release tables solely because they appear in the logical ERD unless doing so is technically necessary and reviewed.

---

---

# 10. Business Decisions Not Required to Start V0.1

The following later-release decisions do not block V0.1:

- tax / VAT design
- multi-currency
- PO over-receipt tolerance
- Supplier Invoice matching tolerance
- retention release
- detailed client progress billing
- detailed cost-recognition policy
- notification delivery channels
- amount-based business approval thresholds

They must be resolved before their dependent later-release functionality reaches implementation.

# 12. V0.1 Exit Boundary

V0.1 is not considered complete until:

- all V0.1 Must Have requirements meet acceptance criteria
- automated critical tests pass
- permissions/security tests pass
- database integrity tests pass
- UAT passes
- no Severity 1 defects remain
- no unaccepted Severity 2 defects remain
- documentation is updated
- Staging validation succeeds
- release deployment / rollback procedure exists
