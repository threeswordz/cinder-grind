# V1.0 Production / Production Readiness — Acceptance Criteria

**Status:** APPROVED — Product / Business Owner, 2026-10-06 (Singapore time)  
**Issue:** #187  
**Acceptance IDs:** AC-V10-001–040

## Production environment / deployment

- **AC-V10-001** — A documented Production environment contract defines required runtime versions, database connection, storage root, web/API origin, secret/configuration inputs and safe defaults.
- **AC-V10-002** — Real Production secrets are external to Git and frontend build variables; safe example files contain names/placeholders only.
- **AC-V10-003** — The application can be built and started reproducibly from an exact approved Git commit with the frozen lockfile.
- **AC-V10-004** — Production deployment applies Prisma migrations only through the approved forward deployment path and verifies migration status.
- **AC-V10-005** — Production traffic is designed for HTTPS; HTTP is redirected or otherwise not used for authenticated Production traffic.
- **AC-V10-006** — Production browser deployment uses same-origin/same-site where practical, or an explicit credentialed CORS allow-list when separated.
- **AC-V10-007** — Startup/restart/shutdown and failed-deployment procedures are documented and tested in a non-Production environment.
- **AC-V10-008** — Deployment remains hosting-provider-neutral and introduces no mandatory paid service without approved Change Control.

## Backup / restore / recovery

- **AC-V10-009** — A consistent PostgreSQL backup procedure exists and records timestamp/source/version/evidence.
- **AC-V10-010** — A Documents storage backup procedure exists and preserves file content needed by database metadata.
- **AC-V10-011** — Backup evidence links database and document-storage backup sets as one logical recovery point.
- **AC-V10-012** — Backup artifacts are access-controlled and are not committed to Git.
- **AC-V10-013** — A restore drill succeeds in an isolated non-Production environment.
- **AC-V10-014** — Restored application/database/storage pass migration status, authentication and document-access checks.
- **AC-V10-015** — Application-only rollback is used only when schema compatibility is explicitly verified.
- **AC-V10-016** — When schema/data recovery is required, the documented database + matching storage restore path is used rather than destructive reverse migrations.

## Security hardening

- **AC-V10-017** — Production session cookies/configuration are secure for HTTPS and preserve approved session invalidation behavior.
- **AC-V10-018** — CSRF protection remains enforced on applicable state-changing authenticated browser requests.
- **AC-V10-019** — Credentialed wildcard CORS is prohibited and allowed origins are configuration-driven.
- **AC-V10-020** — Appropriate security headers are configured and regression-tested.
- **AC-V10-021** — Authentication/login endpoints have open-source/local rate limiting with deterministic test coverage, use a trusted client-identity strategy when deployed behind a reverse proxy, and remain effective across ordinary application process restarts or explicitly delegate that protection to the approved reverse-proxy boundary.
- **AC-V10-022** — Request/body/file-size limits and upload type/filename/path protections are enforced.
- **AC-V10-023** — User-facing errors and operational logs do not expose passwords, session tokens, secrets, raw storage paths or unsafe stack traces.
- **AC-V10-024** — Production interactive API documentation exposure is disabled or explicitly restricted according to configuration.
- **AC-V10-025** — Production dependency audit passes with no unapproved mandatory paid/runtime dependency.
- **AC-V10-026** — Cross-module authorization regression proves Project scope, explicit permissions, technical SYS_ADMIN separation and protected source-detail boundaries remain intact.

## Operations / observability / performance

- **AC-V10-027** — Health/readiness checks expose only non-sensitive service state and can detect unavailable required dependencies needed for safe service.
- **AC-V10-028** — Requests/errors can be correlated through a server-controlled correlation/request identifier.
- **AC-V10-029** — Operational logging is structured/consistent enough to diagnose startup, migration, authentication and server failures without a mandatory external SaaS.
- **AC-V10-030** — A documented log retention/rotation approach prevents uncontrolled local log growth.
- **AC-V10-031** — An operations runbook covers startup/restart, backup, restore, deployment failure and initial incident triage.
- **AC-V10-032** — Representative capacity/performance evidence is recorded for key read and mutation flows without inventing an unapproved contractual SLA.
- **AC-V10-033** — Existing idempotency/concurrency protections for stock, payment, approval and other high-risk material effects pass regression.
- **AC-V10-034** — No production-readiness control requires a paid monitoring/APM/SIEM service.

## Release candidate / exit

- **AC-V10-035** — A clean Production-like deployment rehearsal completes from an exact release-candidate commit.
- **AC-V10-036** — Full applicable CI/regression, schema validation, production dependency audit and authenticated live acceptance pass on the release candidate.
- **AC-V10-037** — A backup/restore rehearsal and rollback/recovery readiness review complete before Production go-live authorization.
- **AC-V10-038** — A non-destructive Production-safe smoke suite is prepared and passes in the Production-like target; if Production deployment is authorized, it is run after deployment.
- **AC-V10-039** — Product / Business Owner performs or explicitly accepts the required V1.0 production-readiness/UAT evidence. Development/CI cannot self-complete this gate.
- **AC-V10-040** — V1.0 Production / production-readiness exit requires explicit Product / Business Owner acceptance / go-no-go authorization.
