## Persisted ownership and compatibility

Seven additive models: HrCompanyAccess, HrEmployment, HrEmploymentRevision, HrPrivateRevision, HrPerson, HrPersonLink and HrReplay. Existing Employee IDs, Company/code, optional User links and Project members remain canonical. No private scalar is added to Employee. New codes use the existing master-code normalization; no numbering format is invented. Enrolment of an existing Employee records only explicitly supplied facts and dates; there is no opening-history backfill. New hires, rehires and Company transfers create a new Employee/code. Explicit predecessor verification requires identity/manage entitlement in both Companies and records protected person links; names and national IDs never auto-merge people. Existing different person groups cannot be merged by this endpoint.

Employment revisions contain pay basis (metadata only), employment form, office/site context, explicit start/end dates and an optional same-Company Project reference. They record HR's verified external hiring-approval reference and correction reason inside authenticated encryption; they execute no hiring approval or recruiting workflow. Office/site approval ownership remains as approved. Project references do not create membership or grant other-module rights. Existing Employee activation/account rules remain unchanged; employment dates do not silently deactivate a linked account.

Database scoped foreign keys prevent Company/Employee/Project mismatch. Private/history/person-link/replay rows are append-only. Employment pointers advance to an existing next revision and a deferred constraint prevents an incomplete enrolment from committing. Explicit expected versions and immutable request receipts prevent silent overwrite. Referenced Employee ID/Company/code changes reject at the database; the existing master edit path locks the row and returns a safe conflict for code changes. Unreferenced Employee edits retain their existing behavior.

## Authorization, replay and privacy

Every service transaction reloads the active user, home Company, actual unrevoked/unexpired session, active Company-owned roles and persisted capabilities. Supplied role/permission arrays confer no authority. Business access requires both the action capability and active target-Company/category entitlement, including the home Company. HR Company selection never changes the session Company, fixed role identity, Project scope or Finance/BOQ authority. Every mutation rechecks its requirements inside the transaction; sorted Company advisory locks and serializable retry protect cross-Company operations and entitlement changes.

Ten capability definitions are added without any role/user assignments. Categories are employment, identity, bank and private documents; view and manage remain distinct. The document capabilities prepare the approved contract but provide no upload/download in this increment. Target-owned `hr.access.manage` can administer another active account's category scope only for its own Company, with version/replay/audit and fixed non-sensitive reason codes. It grants no business reads, cannot change its own scope and cannot administer a foreign target Company; a composite actor/Company foreign key also enforces ownership.

Identity/contact/bank fields and private revision reasons use the reviewed [private core](HR1-A-PRIVATE-CORE.md). Private-request replay fingerprints are keyed and retain their key ID across rotation. Scope administration contains only identifiers, fixed codes and booleans; its versioned canonical digest lets an authorized Company administrator revoke access even when private keys are unavailable. Generic audit stores only actor/target/record/category/version pointers, fixed codes and reason-presence metadata. Cross-Company audit events belong to the authorized target Company while preserving the actual actor; this audit ownership does not change session authorization. No raw value, free correction text, key or original crypto exception is logged or copied into audit/replay.

Private values default to fixed masks; an explicit CSRF-protected reveal of a selected version requires category view authority and writes a metadata-only audit event. Reason text and hiring references are additionally identity-private: employment read alone cannot reveal them, and a bank-only accounting reader cannot read free correction reasons. Private history listings expose only revision pointers, version, actor and time. Missing/wrong/retired keys fail safely on value reads/writes. The global HTTP no-store policy remains. The DTO/input allowlists reject salary, unknown fields, invalid identities/dates and unsupported categories without echoing submitted private data.

## HTTP surface

All routes are under `/api/v1/hr`, existing AuthGuard/PermissionGuard conventions and CSRF for POST. Dynamic identity/bank categories receive their persisted capability/category checks inside the service. Business mutations return only `{id,version}` receipts, including for manage-only callers.

| Route | Purpose / authority |
|---|---|
| GET companies | Explicitly authorized HR Company/category options; no global identity search |
| GET companies/:companyId/employees | Whitelisted register, bounded cursor page; employment/view plus target scope |
| POST companies/:companyId/employees | New canonical Employee and initial history; employment/manage, plus both identity/manage scopes for a verified predecessor |
| GET/POST companies/:companyId/employees/:employeeId/employment | Safe history / reasoned expected-version enrolment or correction |
| POST …/employment/:revisionId/reveal | Audited identity-private reason and verified hiring reference |
| POST …/person-link | Explicit verification against a scoped source episode; never implicit group merge |
| GET …/private/:category and …/history | Masked values / metadata-only revisions; category/view |
| POST …/private/:category/revisions | Expected-version encrypted snapshot/correction; category/manage |
| POST …/private/:category/reveal | Explicit selected-version values; category/view |
| POST …/private/:category/reason | Private correction reason; category/view and identity/view |
| GET/POST companies/:companyId/access | Target-owned technical scope administration; no self-grant. GET returns `{items,nextCursor}`, at most100 grants; continue with `?after=<nextCursor>` to inspect/revoke every active or revoked entry. |
| GET projects/:projectId/employees | Existing persisted Project scope and hr.operational.view; only ID/code/name/job title |
