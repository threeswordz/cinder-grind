## Architecture / dependency boundary

- Preserve existing `apps/web` React 19 + TypeScript + Vite + MUI 7 + TanStack Query; `apps/api` NestJS modular monolith, Prisma + PostgreSQL.
- Reuse existing `apps/web/src/App.tsx` authenticated `/auth/me` access and `AdminConsole.tsx` permission-filtered source section registry. Progressively adapt group navigation rather than deleting 29 working tab/section views at once.
- Existing source modules remain the system of record for Project/WBS/Activity, BOQ/Procurement, Inventory, Subcontracts, Finance, Cost, Management and Documents. WBS and Cost Code are independent.
- Open-source / zero-cost-first (DEC-008); no mandatory paid runtime/hosting/provider, new identity platform, library or API gateway. Evaluate any dependency with license/size/security/cost justification before an approved implementation commit.
- **Stage A schema/data changes: NONE.** No changes to already executed migrations. Future migration, if owner-approved in a distinct scope, must be forward-only, reversible by runbook rather than destructive history editing, with tested upgrade/fresh migration evidence.

## Identity, authorization and source data contracts

1. Server-authenticated `/auth/me` provides signed-in `id`, `companyId`, `roleCodes`, `permissions`, `displayName`, `email`. Client has no role switcher or impersonation identity. **Verified source-code permission inventory vs the eight personas is in `V1.1-ROLE-PERMISSION-IMPLEMENTATION-MATRIX-PROPOSAL.md`; actual user Role/Project/Approval Matrix settings remain unknown without authorized UAT evidence.**
2. Company context is **not freely selectable** unless approved existing API/session authority permits it. Project selector only lists backend-derived effective Project access. No client-side fake allowlist or implicit all-project reports.
3. Navigational grouping may use existing permissions to *hide* inapplicable UI, but every detail/aggregation/action endpoint enforces source-module `permission`, Company, Project membership, status, approval step and maker/checker rules. Technical SYS_ADMIN is separate from business approvers.
4. Any new read-only Workbench API is a **candidate only**. First use authorized existing source list APIs and cache keys scoped by user+Company+Project. For an approved aggregation endpoint: document resource families, typed DTO, permission and list-vs-count parity, pagination, minimum necessary columns, bounded response sizes, no cross-module source details, explicit negative tests.
5. A "my approval" card is eligible only if actual source status, configured approver Role/step, maker/checker and Project/Company tests concur; having a generic `*.approve` permission does not prove a pending approval is "mine".
6. A new UI screen must not invent a source transition such as "Goods Receipt confirmation by Jai" before a separately approved domain rule provides it. Keep all existing transaction creation/approval/return/reverse mutations in owning NestJS services.
7. No new mutable transaction ledger, duplicate documents/source row ID, shadow approval engine, cross-Project Finance Invoice/Payment, VAT/WHT/GL, fixed assets or HR/payroll model.
8. Display currency only from existing stored source Company/base currency and document currency rules. No FX, new balances, model reinterpretation or rounding logic in dashboards.
9. Document links/attachments require both document permission and owning source target view permission; no raw blob public URL, insecure cross-project detail or alternative storage.

## New optional support diagnostics — not in default implementation

- Product Owner supported the **concept** of read-only administrator troubleshooting via the admin's own login. Proposed `admin.user_diagnostics.view` is **not a current approval** and must not be seeded in V1.1 B/C without a distinct owner decision.
- If later authorized: same-Company target-user query, non-enumerating error shape, redacted role/permission/approval/Project explanation, audit of requester/target/purpose, no protected document amount/status disclosure without source authority, no impersonation/mutating API, zero secret/session log leakage.
- Current operational log captures path/status/duration/correlation IDs, not necessarily per-user events. Future user-specific support log correlation needs separate security/data retention design. Details and AC-V11-031–036 are in `V1.1-USER-SUPPORT-DIAGNOSTICS-PROPOSAL.md`.
- **DEC-022:** independent exact-green-candidate review for auth, cross-user data, finance, stock, approval, pagination/count leak or schema/rule changes; do not continuously request Codex per small visual commit.
