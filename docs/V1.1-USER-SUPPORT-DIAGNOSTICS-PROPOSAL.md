## Goal

An **authorized support administrator uses their own account** to investigate why another assigned user (example: "Chai") cannot see, submit or approve an action. No need for the affected user's credentials and **no Switch Role, View-As, impersonation or live-session takeover**.

Diagnostic questions:
1. Is the user active, linked to an active Employee, and assigned the expected active Role(s)?
2. Is an expected permission missing from the effective assigned-role permission set?
3. Does the user have persisted effective Project membership for the record, or an approved assignment-filter bypass *without* additional business authority?
4. Is the configured Approval Matrix step eligible for the user's active Role(s), and does maker/checker block action?
5. Is the target transaction in a state that permits the desired action? If not, return an approved **redacted reason** without business record detail.
6. Does a user-provided correlation/request ID match a safe operational error record? If no correlation exists, ask for a report/reference and do not invent user-specific error history.

## Proposed UI — Administration > User Support & Diagnostics

- Search a **Company-scoped** authorized user by name/account reference. Show minimal profile: display name, active state, linked Employee status, assigned Role codes, *non-sensitive* effective permission summary.
- Read-only diagnostic workspace with tabs: **Account & Roles**, **Permissions**, **Project Access**, **Approval Eligibility**, **Reported Issue / Correlation ID**, and **Diagnostic History** (only when support access audit exists).
- A support admin selects a supported **operation type** (e.g., "Approve Purchase Order") and optional record reference supplied by the user; the backend evaluates *existing* rules in a **dry-run / explanation** path, never executing the user's action and never bypassing the owning module's permission checker.
- Example output: `MISSING_PERMISSION`, `APPROVAL_STEP_NOT_ELIGIBLE`, `PROJECT_NOT_ASSIGNED`, `MAKER_CHECKER_BLOCKED`, `INVALID_DOCUMENT_STATE`, `BUSINESS_VALIDATION_FAILED`, `REQUEST_ERROR`, `INSUFFICIENT_EVIDENCE`. These are **proposed safe labels**, not existing API contract or guaranteed explanations.
- For unrelated or inaccessible transactions, hide document number, amount, customer, supplier, attachment, detailed state, protected cross-module content and counts. Return a generic `INSUFFICIENT_AUTHORIZED_CONTEXT` outcome where safer than revealing object existence.
- Display authorized "what to check next" guidance (e.g. contact configured PO approver; assign permitted Project membership) without auto-reassigning roles, approving payments or changing workflow state.
- Normal User Management remains the only administrative authority to modify eligible assignments, under its existing guards/audit; this diagnostics page has **no mutation controls**.
- No remote screen/cursor sharing; browser issues may require the user to share a screenshot or correlation ID.

## Server-side design constraints

1. Require an explicitly configured diagnostic read permission, **proposed** `admin.user_diagnostics.view` (not presently proven to exist), plus validated same-Company target-user scope and support-purpose checks. Do not assign it to all users or implicitly to SYS_ADMIN without the approved role/permission decision. This must be a permission design decision, not a UI-only gate.
2. Introduce a bounded read-only API only *after* approved stage design. Do not expose a generic arbitrary-model search, arbitrary user token, session cookie or an action-execution-as-user endpoint.
3. Query current persisted Role and Employee/Project membership for the **target user**. The diagnostic request **is not an authorization grant** to the support admin to open the target's protected transactions.
4. Approval eligibility explanation must reuse the canonical approval rules. Be explicit where no shared dry-run evaluator exists: report `INSUFFICIENT_EVIDENCE` instead of guessing or cloning approval logic.
5. Keep the subject and requester User IDs separate; audit `actorAdminUserId`, `targetUserId`, purpose/reason, timestamp, permitted diagnostic category and correlation ID when available. No password, token, CSRF, session ID, raw headers/URL query or sensitive business values in diagnostics/audit.
6. Respect data-minimization and retention controls. Limit search and enumeration, redact errors, and ensure support endpoints themselves cannot leak multi-company user existence or Project data.
7. Account status, permission and scope checks may be read-only. Do not "test" a transactional approve or financial post endpoint using another user's credentials.
8. Existing operational logs lack enough fields for a guaranteed user-specific log trail. Any future actor-context correlation or client error reporting is separately security-reviewed and avoids sensitive body capture.

## Proposed acceptance criteria — *additional, unapproved* AC-V11-031–036

- **AC-V11-031**: Authorized admin opens a Company-scoped user's read-only diagnostic summary without session takeover, role switching or knowing their password.
- **AC-V11-032**: Effective permission, employee/project membership and supported approval eligibility diagnostics match backend source rules; an unavailable explanation is marked unknown rather than invented.
- **AC-V11-033**: Protected business details, cross-Company users, inaccessible Project names/record existence and counts do not leak through diagnostic responses or timing/error shape; negative API tests prove isolation.
- **AC-V11-034**: Diagnostic reads are themselves access-controlled and audited with requester, target, time, purpose; never contain credentials, session/CSRF tokens, sensitive record payloads or unsanitized operational logs.
- **AC-V11-035**: Correlation-ID support shows only actual appropriately retained safe events. The UI never claims that existing operational logs already identify a specific user when they do not.
- **AC-V11-036**: Separate authenticating users and test fixtures demonstrate an affected user blocked at a configured approval step or Project boundary and an administrator diagnosing the safe reason **without** gaining business approval authority.

These criteria are **proposals only**, not existing acceptance evidence. Implementation needs explicit release scope/permissions/API approval and stable-candidate independent Codex review because authorization and data isolation are high-risk.

## Product decisions still required

- Which administrator support role(s) get `admin.user_diagnostics.view` and whether admins may diagnose other Company users (recommended NO)?
- May a diagnostic reveal a protected transaction's existence/status to a support user who lacks the source-module permission? **Recommended no**; return a redacted reason only.
- Which context can an end user supply (reference/correlation ID/approximate time), and how long should diagnostic audit and request logs be retained?
- Should the minimal diagnostics slice ship in V1.1 or be deferred as future scope? It changes backend authorization surfaces and demands its own security review.
