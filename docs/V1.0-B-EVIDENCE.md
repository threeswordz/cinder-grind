## Initial DEC-022 review findings

Codex reviewed exact head `1cdeb4b6c5ec07470002eb1cb0e402abc49f41db` and identified three genuine findings:

1. **P1 — same database under another Prisma schema:** restore isolation included the Prisma `schema` query parameter even though `pg_restore` operates on the database after that parameter is removed.
2. **P1 — whole-file backup hashing:** `manifest.mjs` used `readFileSync` for recovery artifacts, which could exhaust Node memory/buffer limits as backups grow.
3. **P2 — textual recovery path containment:** repository/Documents containment checks could be bypassed by path aliases such as `..` or symlinks.

## DEC-022 remediation

All three findings were fixed without weakening the fail-closed recovery model:

- `postgres-identity.mjs` now defines database identity using hostname + port + database name, ignoring Prisma schema; `restore-drill.sh` rejects any target matching the source database identity.
- `manifest.mjs` now hashes `database.dump` and `documents.tar.gz` using `createReadStream` and incremental SHA-256.
- `path-safety.mjs` canonicalizes existing path ancestors with `realpath`, preserves missing suffixes, and performs boundary-aware repository/Documents containment checks.
- `ci-safety-regressions.sh` explicitly proves rejection of same-database/different-schema restore targets, `..` repository aliases, and symlinked recovery roots inside Documents storage.

## Final DEC-022 re-review findings and second remediation

Codex re-reviewed exact head `29dec350c316d253ead48aeca8a1c1723edfb21f` and identified three additional genuine findings:

1. **P1 — hostname/DNS alias database identity:** URL hostname comparison could treat `localhost` and `127.0.0.1` (or two DNS aliases) as different even when both reach the same PostgreSQL database.
2. **P2 — restore storage containment:** an empty `RESTORE_STORAGE_ROOT` nested inside live `STORAGE_ROOT`, or containing live storage, was not rejected.
3. **P2 — whole-file restored-document hashing:** the restored Document verifier still used a whole-file read for SHA-256 and could exhaust memory on very large valid files.

Second remediation head `1b73482f95f505e68d2af0095c1a19c58ac096cd` fixes all three without expanding V1.0-B scope:

- PostgreSQL identity is now obtained through live `psql` connections from connected server address + server port + `current_database()`, after removing Prisma-only `schema`; CI proves `localhost` / `127.0.0.1` plus schema aliases resolve to the same identity and are rejected as a restore target.
- restore storage is canonicalized and must be disjoint from live Documents storage in both directions before target creation or archive extraction; CI covers both nested directions.
- restored Document checksums use `createReadStream` with incremental SHA-256 rather than `readFile`.
