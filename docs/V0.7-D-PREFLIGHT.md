## Scope and requirement trace

Stage D implements the Project Variations / Revenue / Profit portion of the approved V0.7 Cost Control baseline under D07-04/05/06/08/09/10, BR-V07-01/03/09–11/13–16 and applicable AC-V07-016–020/025–043/047–050. It reuses the completed Stage-A integrated source read model, Stage-B Direct Cost Actual source and Stage-C Forecast measures.

- Persist Cost Control-owned client/project commercial Variations, distinct from V0.5 subcontract Variations.
- Project Variation values are signed positive/negative `value_delta` amounts.
- Only approved, non-reversed Project Variations affect Revised Contract Value.
- Original Contract Value remains Project-owned and cannot be overwritten by Cost Control.
- Revised Contract Value = Original Contract Value + approved non-reversed Project Variation deltas.
- Actual Revenue = final-approved Client Invoice totals.
- Cash Received = approved, non-cancelled INBOUND Payments.
- Forecast Revenue = Revised Contract Value.
- Actual Profit = Actual Revenue − Actual Cost.
- Forecast Profit = Forecast Revenue − Forecast Cost.
- Billing, cash received, forecast revenue, actual revenue and profit remain explicit separate measures.
- Revenue/profit remain Project-level where canonical source records do not provide an approved lower-dimensional allocation. No synthetic WBS/Cost Code revenue allocation or profitability is permitted.
- Project Variation financial effect uses approval date under D07-08.
- Base-currency-only and PostgreSQL/Prisma Decimal remain authoritative.

## Technical pre-flight

- Modular monolith / existing PostgreSQL + Prisma / existing React workspace; no new runtime service or mandatory paid dependency.
- Forward-only migration(s) for `project_variations` and required lifecycle/history/replay/integrity guards; executed migrations remain unchanged.
- Reuse Company isolation, database-derived effective Project access and explicit `cost.variation.view/create/submit/approve`; `projects.access_all` and SYS_ADMIN grant no implicit Project Variation commercial authority.
- API family: `/api/v1/cost-control/project-variations` under the approved baseline; backend authorization remains mandatory.
- Draft create/edit; submit; approval/rejection under configured Approval Matrix and maker-checker; approved rows are immutable.
- Correction is by linked compensating reversal, not silent edit/delete.
- Immutable variation numbering must be deterministic and safe under concurrent creation.
- Sensitive create/action/reversal requests must be idempotent and concurrency-safe so retries or races cannot duplicate commercial effects.
- Revised Contract Value and Forecast Revenue derive from Project + approved/non-reversed Project Variation source state; they are not stored as a second editable total.
- Actual Revenue derives from final-approved Client Invoice totals and Cash Received from approved/non-cancelled INBOUND Payments; Stage D must not mutate Finance-owned records.
- Actual Profit and Forecast Profit must use the approved revenue/cost bases and Stage-A/Stage-C authoritative Decimal measures without cash/cost-state conflation.
- Revenue/profit dimensional output remains Project-level unless a future approved canonical allocation exists; no proportional allocation is introduced.
- Unsupported non-base currency sources fail closed under D07-09.
- Source evidence remains read-only and permission-sanitized under D07-10.
- Any new business policy, permission, dependency, editable revenue ledger, synthetic allocation or scope beyond the approved baseline requires explicit Change Control.
