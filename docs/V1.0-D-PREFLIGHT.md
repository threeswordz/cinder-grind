## Planned implementation boundaries

### D1 — Readiness and server-controlled correlation
- preserve a small non-sensitive liveness/readiness surface;
- distinguish simple process liveness from safe-service readiness where useful;
- readiness must fail when required PostgreSQL or Production Documents storage is unavailable;
- never expose raw storage paths, connection details, credentials or business data;
- generate the authoritative correlation/request ID on the server;
- if an inbound trace hint is retained, keep it separate from the server-owned ID;
- retain correlation ID in safe error responses and operational logs.

### D2 — Structured local logging and retention
- define one consistent machine-readable operational log shape suitable for stdout/stderr and local/self-hosted collection;
- cover request/server failures and operationally useful authentication/startup context without logging secrets;
- preserve V1.0-C redaction guarantees;
- document provider-neutral rotation/retention using native/open-source host/container facilities;
- no mandatory SaaS logger, APM or SIEM.

### D3 — Operations runbook and failure visibility
- add a canonical operations runbook linking the existing Production deployment and recovery procedures;
- cover service health/readiness interpretation, restart, backup/restore references, deployment failure, initial incident triage, correlation-ID log lookup, containment and evidence capture;
- preserve forward-only migrations and compatibility-aware rollback;
- do not create destructive Production diagnostics or self-authorize go-live.

### D4 — Representative performance / capacity evidence
- provide a reproducible non-Production benchmark path with deterministic setup and bounded runtime;
- exercise representative read and mutation flows using realistic authenticated application paths where practical;
- record fixture size, test environment, concurrency, latency/throughput observations and caveats;
- treat results as evidence for the tested environment only;
- do not invent an SLA, concurrency promise or hosting-size guarantee.

### D5 — Material-effect concurrency/idempotency evidence
- explicitly map and retain stock posting/reversal locks/effect keys;
- retain Payment create-key/action replay and settlement protections;
- retain approval decision serialization and duplicate-decision prevention;
- retain Subcontract claim contention protections and other already-delivered high-risk guards;
- add only the minimum D-stage regression/evidence needed to make AC-V10-033 explicit and deterministic;
- preserve all existing Project scope, permission, audit and maker-checker semantics.
