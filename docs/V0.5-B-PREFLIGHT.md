## Agreement lifecycle and revision contract

- Initial agreement fields remain editable only while the original record is Draft and has never been submitted.
- Submission creates retained revision Version 1 containing the agreement's original value, Scope of Work, currency and proposed operational status snapshot, links a configured `SUBCONTRACT_AGREEMENT` Approval Instance and records maker/time.
- Final approval is maker-checker controlled. It locks and reloads the agreement/revision, records the first-approved checkpoint and makes original value, Scope of Work, currency, Project, Subcontractor, number and creator immutable at the database boundary.
- Rejection retains the revision, Approval Instance and action history. Submitted or decided revisions are never edited or deleted.
- A later administrative revision is a new numbered Draft version with required reason and a fresh Approval Instance on submission. It copies the immutable commercial snapshot and may change only the already-approved non-commercial configured operational status. Stage B introduces no new dates, terms, references or other administrative business fields.
- Approval of an administrative revision updates the agreement's current operational status without changing original value, Scope of Work, currency or commercial ceiling. Earlier versions stay readable.
- If another administrative field is later required, implementation stops for approved scope/data Change Control rather than inventing it.
- Agreement cancellation applies only to an approved, non-cancelled agreement, requires reason/actor/time and locks the agreement. In Stage B it is denied for a submitted Work Order or any active approved Work Order allocation. Later stages extend the same guard for pending Variations, active Claims and non-reversed certifications.
- Configured operational status remains descriptive and separate from system approval/cancellation state; no status label grants approval authority or silently changes Work Order eligibility.

## Work Order data contract

- `SubcontractWorkOrder` belongs to one Company, Project and approved agreement. It stores immutable agreement-local `WO-###` identity plus integer sequence, required scope, positive tax-exclusive DECIMAL(18,2) amount, optional same-Project WBS, optional same-Company Cost Code, Approval Instance, creator/submitter timestamps and retained decision history.
- Currency is inherited from the agreement and returned explicitly by the API; no independent Work Order currency input, tax calculation or FX conversion exists.
- Draft-only fields are editable. Submission freezes scope, amount and dimensions and starts the configured `SUBCONTRACT_WORK_ORDER` Approval Matrix. Approved/rejected history cannot be edited or deleted.
- Work Order cancellation/reversal is not introduced because BR-V05-07 approves Draft → Submitted → Approved/Rejected only. Any later allocation-release lifecycle requires Change Control.
- Creation and final approval both require the agreement to be approved and not cancelled. Final approval locks the agreement, rechecks lifecycle/references and sums active approved Work Orders.
- In Stage B the current authorized ceiling is the original approved agreement value. Later approved Variation deltas extend the same derived ceiling in Stage E. Work Orders allocate within this ceiling and are never added to it as a second commitment.
- Agreement-local numbering allocation and approval use the same agreement lock namespace. Retained rejected identifiers mean `WO-###` is never reused.

## Concurrency and integrity baseline

1. Agreement submission/revision creation, agreement cancellation, Work Order numbering and Work Order final approval share deterministic agreement-row locking.
2. Concurrent Work Order approvals cannot allocate above the original approved ceiling.
3. Concurrent cancellation versus Work Order submission/approval has one valid winner; the losing action rechecks state after the lock and fails without a partial Approval Action or audit row.
4. Final agreement/Work Order approval revalidates current workflow state, Project/Company references and immutable payload after locks are held.
5. Stable retry keys return an existing result only for the same authorized actor/action/material payload. A changed payload conflicts.
6. No action relies on configured status labels, UI visibility or technical SYS_ADMIN role codes for business authority.
