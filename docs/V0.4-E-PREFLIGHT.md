## Stock Transfer data and workflow contract

### Header and items

- Add `stock_transfers` with Company, `STYYMM-###` transfer number, source/destination Warehouse, transfer date, Approval Instance, creator/submitter/poster/reverser, post/reversal keys, remarks/reversal reason and actor/time history.
- Add `stock_transfer_items` with line number, Material, positive DECIMAL(18,4) quantity, UOM, source Project attribution and destination Project attribution. Source and destination Project are explicit per line because a general Company Warehouse may contain separately Project-attributed stock.
- Source and destination Warehouses must differ and belong to the same Company. Project-fixed Warehouses require matching Project attribution; a general Warehouse may hold an accessible Project attribution.
- Project attribution is preserved by default. An explicit attribution change is accepted only when the actor has effective access to both source and destination Project contexts and the destination Warehouse permits the target Project. The source/destination attribution change is retained in Transfer and audit history.
- Stage E does not invent Transfer-level WBS/Cost Code/Activity reassignment. Those Issue allocation dimensions remain historical ledger traceability; Project attribution is the approved Transfer allocation boundary.
- Draft data is editable only while Draft. Submitted/approved/rejected/posted/reversed history is retained and protected from rewrite/delete.

### Approval and posting

- Transfer lifecycle is Draft → Submitted → Approved/Rejected using Approval Matrix workflow `STOCK_TRANSFER`; final approval and physical posting occur atomically.
- The creator cannot perform final approval/posting. Rejection retains submitted history and approval action evidence.
- Final posting acquires deterministic advisory locks for both Warehouses ordered by Warehouse id, then row-locks/revalidates both Warehouses and locks controlled stock dimensions in deterministic order.
- Recompute source on-hand and Active Reservation quantity after locks are held. Posting rejects source quantity that would create negative on-hand or negative availability beneath Active Reservations.
- Retry with the same post key returns the existing posted Transfer; a different source cannot reuse the effect key.

### Immutable ledger effects

- Extend `stock_transactions` with nullable Transfer header/item source links while preserving exactly one source family for every original physical movement.
- Each posted Transfer item creates exactly two atomic ledger effects: `STOCK_TRANSFER_OUT` as the source-negative row and `STOCK_TRANSFER_IN` as the destination-positive row for the same Material, quantity and UOM.
- Source row uses source Warehouse/Project attribution; destination row uses destination Warehouse/Project attribution. Company and UOM are identical and no UOM conversion is introduced.
- Database constraints/source triggers validate the matched Transfer source, direction, dimensions and exact quantity independently of application code.
- Full reversal is atomic and appends exact opposite rows `STOCK_TRANSFER_OUT_REVERSAL` and `STOCK_TRANSFER_IN_REVERSAL`, each linked through `reversal_of_id`. Reversal is idempotent and must not create duplicate effects.
- Reversal revalidates that the destination-negative reversal cannot create negative stock or violate Active Reservation availability at the destination. Warehouse archival races serialize on the same Warehouse locks.
- No second ledger, editable balance, transfer-in-transit store or valuation layer is introduced.

## Reporting and traceability contract

- Add read-only Inventory report endpoints under `/api/v1/inventory/reports` protected by `inventory.report.view`.
- Balance report derives from `stock_transactions` and may share the Stage-C balance query. Supported filters include accessible Project, Warehouse, Material, active/inactive Warehouse and zero-balance behavior.
- Movement report derives directly from immutable `stock_transactions` and supports accessible Project, Warehouse, Material, movement/source family and posted date range filters.
- Movement rows expose movement type, signed quantity, Warehouse, Project attribution, Material/UOM, actor/time and stable source identity sufficient to navigate traceability to Receipt, Issue, Return or Transfer.
- Source-number/detail lookup is derived from canonical source documents; no copied editable reporting ledger is created.
- Reporting never exposes valuation, unit cost, accounting journal, Supplier Invoice/payment or Finance posting fields in V0.4.
- Project authorization applies before aggregate/report results; unauthorized Project activity cannot be inferred through counts, filters or source references.

## Concurrency and integrity baseline

1. Transfer locks both Warehouse ids in sorted order so concurrent A→B and B→A Transfers cannot create an advisory-lock cycle.
2. After Warehouse locks, source/destination stock-dimension locks are acquired in deterministic key order and balances/Active Reservations are recalculated.
3. Concurrent Transfers, Issues, reversals or Warehouse archival cannot consume the same final source availability twice or leave positive stock in an archived Warehouse.
4. Transfer reversal locks destination stock before reducing it and rejects negative stock or Active-Reservation undercut.
5. Post/reversal/source uniqueness plus stable effect keys prevent duplicate physical effects on retry/concurrency.
6. Any failed approval, audit, Transfer state change or ledger row rolls back the complete action.
7. Database triggers continue to reject ledger UPDATE/DELETE and mismatched source/dimensions independently of application code.
