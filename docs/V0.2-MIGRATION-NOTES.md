# Construction ERP — V0.2 Migration Notes

## V0.2-B Scheduling Engine

### Milestone integrity upgrade

V0.2-B introduces the approved milestone rule:

- milestone duration = 0 work days
- milestone planned start = planned finish

V0.2-A allowed milestone-shaped rows that did not satisfy this rule. The V0.2-B migration therefore adds `activities_milestone_schedule_check` as a PostgreSQL `NOT VALID` check constraint.

This is intentional:

- PostgreSQL enforces the constraint for all new and updated rows after the migration.
- Existing V0.2-A rows are not silently rewritten.
- Deployment does not fail merely because an older row was valid under the earlier implementation.
- The Scheduling Engine rejects an invalid legacy milestone when schedule analysis encounters it.
- An authorized user must correct the Activity through the normal Activity workflow before that legacy row can be updated successfully.

Do not auto-normalize legacy milestone dates or durations in a database migration because that would rewrite business schedule data without owner review.

After all legacy rows have been reviewed/corrected, a future controlled migration may run:

```sql
ALTER TABLE activities
VALIDATE CONSTRAINT activities_milestone_schedule_check;
```

Validation must be performed only after confirming no non-compliant legacy milestone rows remain.

### Dependency graph concurrency

The V0.2-B dependency-cycle trigger takes a transaction-scoped PostgreSQL advisory lock keyed by Project before checking reachability. This serializes dependency-graph mutations for the same Project and prevents concurrent opposite-edge inserts from committing a circular graph under `READ COMMITTED`.

The lock is Project-scoped; dependency mutations for unrelated Projects remain independent.


## V0.2-C Baselines / Progress

### Additive schema change

V0.2-C adds:

- nullable `projects.actual_start_date` and `projects.actual_completion_date`
- `schedule_baselines`
- `schedule_baseline_activities`
- `activity_progress`
- Stage C permissions for baseline submission/approval and progress recording

The migration does not rewrite existing V0.1/V0.2-A/V0.2-B Project or Activity schedule data. Existing Projects receive null actual dates until an authorized user records them.

### Baseline immutability and versioning

A submitted Schedule Baseline is a versioned immutable snapshot of the active Project Activities and the backend-calculated planned schedule at submission time.

- Version numbers are unique per Project.
- Rebaseline creates Version N+1.
- Approval uses the existing configurable Approval Matrix with entity type `SCHEDULE_BASELINE`.
- The current reporting baseline is derived as the highest-version approved baseline; old approved versions remain historical and are not mutated.
- Snapshot rows cannot be updated or deleted.
- Baseline metadata cannot be changed after its approval instance is attached.

This prevents the baseline tables from becoming a second editable schedule source.

### Activity Progress history

`activity_progress` is append-only:

- percent complete is constrained to 0–100
- corrections create a new entry rather than rewriting history
- update/delete is rejected at the database layer
- the current percentage is derived from the latest appended entry (creation order), even when that entry corrects an earlier progress date
- `source_type` and optional `source_entity_id` allow the later V0.2-E Daily Site Report workflow to append through the same history without redesigning the table

### Project/company scope

Database triggers verify:

- Schedule Baseline Project/submitter/approval-instance company and entity scope
- baseline snapshot Activity/WBS membership in the Baseline Project
- Activity Progress Project/Activity/company/recorder consistency

Backend Project-scope authorization remains mandatory in addition to these database integrity controls.

### Approval and permissions

New permissions:

- `schedule.baseline.create`
- `schedule.baseline.approve`
- `schedule.progress.record`

The System Administrator role receives technical permission provisioning consistent with earlier migrations, but approval still requires authorization by the configured Approval Matrix role. System Administrator status by itself is not business approval authority.

### Delay comparison

Delay and variance are derived rather than persisted:

- current approved baseline finish is the comparison reference
- explicit Activity forecast finish takes precedence; otherwise the backend Scheduling Engine calculated forecast is used
- signed variance is measured using the Activity Working Calendar
- positive = DELAYED, zero = ON_TIME, negative = AHEAD
- without a current approved baseline, delay is UNAVAILABLE and delay work days is null
