# Construction ERP — V0.3 Proposed Business Rules

**Status:** DRAFT — PRODUCT / BUSINESS OWNER APPROVAL REQUIRED  
**Purpose:** Resolve rules that are not fully determined by the approved requirement wording before implementation.

These proposals are deliberately conservative and preserve the existing architecture/release boundaries.

---

# BR-V03-01 — BOQ ownership and cardinality

**Proposed rule**

A Project has one canonical BOQ commercial structure for V0.3. Sections/items keep stable identities. Commercial budget changes are represented by approved Budget revisions rather than by creating unrelated competing BOQs for the same Project.

No cross-Project BOQ item is permitted.

---

# BR-V03-02 — BOQ / PO arithmetic

**Proposed rule**

- quantity and rate are decimal values
- quantity must be greater than zero
- rate must be zero or greater
- amount is backend-calculated as quantity × rate
- UOM is required for measurable lines
- V0.3 does not calculate tax/VAT, FX or accounting postings
- the persisted/calculated amount is the authoritative line amount for V0.3 reporting

Exact decimal scale follows database-safe commercial precision and is validated consistently across API/database/tests.

---

# BR-V03-03 — Budget baseline and revisions

**Proposed rule**

- a new Budget revision starts as DRAFT
- approval uses the existing configurable Approval Matrix with maker-checker enforcement
- the first APPROVED revision is the immutable **Original Budget**
- the highest/latest APPROVED revision is the **Current Revised Budget**
- approved revisions are immutable history
- rejected revisions remain history but never become current
- a later revision never overwrites the Original Budget

---

# BR-V03-04 — Budget allocation dimensions

**Proposed rule**

Project is inherited/required from the BOQ/Budget owner.

WBS and Cost Code are independent optional allocation dimensions at item/revision-line level:
- if WBS is supplied it must belong to the Project
- if Cost Code is supplied it must belong to the Company and remain independent of WBS
- unallocated values remain reportable as unallocated rather than being forced into a false WBS/Cost Code relationship

---

# BR-V03-05 — Procurement line type

**Proposed rule**

PR/RFQ/quotation/PO lines support:
- MATERIAL — references an active Material master
- SERVICE — uses a controlled line description and UOM without creating a fake Material master record

A line cannot be both types. This preserves Material master ownership while allowing service procurement required by PO requirements.

---

# BR-V03-06 — Purchase Request lifecycle

**Proposed rule**

PR lifecycle:
- DRAFT
- SUBMITTED
- APPROVED
- REJECTED
- CANCELLED

Only DRAFT is directly editable.

Submission/approval/rejection uses the Approval Matrix. Approved PR demand is retained as history. Cancellation is a retained state transition, not physical deletion.

A rejected PR may be copied/revised into a new draft transaction; the rejected record itself is not silently rewritten.

---

# BR-V03-07 — Required-on-Site context

**Proposed rule**

Required-on-Site is stored at procurement-demand line level.

A line may optionally reference an Activity. If an Activity is supplied it must belong to the line Project.

Required-on-Site is procurement-owned planning data. It never changes the Activity planned/baseline/forecast dates automatically.

---

# BR-V03-08 — RFQ sourcing scope

**Proposed rule**

An RFQ is created from one or more APPROVED PR lines within one Project.

The same approved PR line may be referenced by RFQ history, but active award/PO quantity controls must prevent procurement beyond the approved demand quantity unless a future explicit override rule is approved.

Multiple active Suppliers may be invited.

---

# BR-V03-09 — Supplier quotation identity / comparison

**Proposed rule**

A Supplier has one current quotation submission per RFQ, with line-level price/quantity/remarks against the RFQ lines.

Quotation comparison is derived from canonical quotation lines. It must not copy supplier prices into a separate manually editable comparison ledger.

Quotation corrections before award update the supplier's draft/current quotation with audit history; award freezes the compared commercial source used for that award.

---

# BR-V03-10 — Supplier award granularity

**Proposed rule**

Supplier selection is **line-level**, allowing different RFQ lines to be awarded to different Suppliers.

A whole-RFQ award is represented by selecting the same Supplier for all lines.

Each awarded line records its source quotation line and decision context.

---

# BR-V03-11 — Purchase Order source and scope

**Proposed rule**

A PO belongs to one Company, one Supplier and one Project in V0.3.

PO lines originate from awarded quotation lines where the competitive sourcing path is used. Direct/manual PO creation is not part of the default V0.3 flow unless separately approved.

PO lines retain PR → RFQ → quotation → award source references.

---

# BR-V03-12 — Purchase Order lifecycle / revisions

**Proposed rule**

PO lifecycle:
- DRAFT
- SUBMITTED
- APPROVED
- REJECTED
- CANCELLED

Only DRAFT is directly editable.

Approval uses the existing Approval Matrix and maker-checker controls.

After first approval:
- commercial changes create a new PO revision/version
- earlier approved revisions remain immutable
- the latest approved revision is current
- cancellation is retained with actor/time/reason
- rejection never creates commitment semantics

---

# BR-V03-13 — Delivery dates and schedule risk

**Proposed rule**

Required-on-Site and Expected Delivery are line-level dates.

Risk classification is backend-derived:
- Expected Delivery > Required-on-Site → AT_RISK
- Expected Delivery <= Required-on-Site → ON_TIME
- either date missing → UNAVAILABLE

The comparison uses calendar dates, not Scheduling working-day arithmetic.

Risk is informational and does not alter Activity dates.

---

# BR-V03-14 — V0.3 cost semantics

**Proposed rule**

V0.3 retains approved PO commercial values and source traceability only.

V0.3 does not:
- recognize Actual Cost
- post Inventory
- create Supplier Invoices
- create Payments
- implement the V0.7 Committed Cost ledger/read model

Later Cost Control may derive commitment from approved PO history; V0.3 must preserve the necessary immutable source values.

---

# BR-V03-15 — Procurement Documents

**Proposed rule**

If DOC-007 is delivered, PR/RFQ/quotation/PO documents reuse the existing secure Documents storage/authorization architecture with canonical Project linkage plus validated transaction linkage.

No procurement-specific file store is introduced.

---

# BR-V03-16 — Forward/backward traceability and deletion

**Proposed rule**

The V0.3 chain retains stable references:

PR line → RFQ line → Supplier quotation line → award → PO line.

Supported screens/APIs expose both source and downstream references.

Submitted/approved/rejected/cancelled commercial transactions and approved budget revisions are not physically deleted through ordinary application flows.

---

# BR-V03-17 — Business numbering

**Decision required**

The requirements require stable business identity but do not define number format.

Proposed baseline:
- system-generated, Company-unique immutable document numbers
- separate sequences for Budget revision, PR, RFQ and PO
- numbering occurs when the transaction is created
- number is never reused after cancellation/rejection

The exact human-readable format should be approved before V0.3-B so it remains stable across UI/API/export use.

---

# BR-V03-18 — V0.3-A implementation gate

V0.3-A BOQ & Budget may begin after:
- V0.3 Scope Baseline is approved
- V0.3 Acceptance Criteria Baseline is approved
- BR-V03-01 through BR-V03-04 and the applicable numbering convention are approved or explicitly deferred

Later-stage rules may be confirmed before their respective implementation stage, but no affected stage may code an unresolved business rule silently.
