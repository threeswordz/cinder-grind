# Construction ERP — V0.2 Deployment / Rollback / Smoke Procedure

**Release:** V0.2 Project & Scheduling  
**Database:** PostgreSQL  
**Document storage:** configured provider behind the existing Documents storage abstraction

## 1. Preconditions

Before deployment, record the exact approved V0.2 commit and ensure the target environment provides the repository-approved Node.js/pnpm toolchain, reachable `DATABASE_URL`, writable document `STORAGE_ROOT`, API/web origins/session configuration, upload policy and secrets outside Git.

For an existing environment, take a consistent PostgreSQL backup and matching document-storage backup before applying V0.2 migrations.

## 2. Deployment

From the exact approved release candidate:

1. install the frozen dependency graph;
2. generate Prisma Client and validate the schema;
3. run the production dependency audit;
4. apply migrations with `prisma migrate deploy`;
5. verify `prisma migrate status` is up to date;
6. build API and web workspaces;
7. start/restart the application using the target environment's approved process;
8. confirm health/startup logs contain no migration or application error.

Never use `prisma migrate reset` against retained UAT or Production data.

## 3. V0.2 smoke checks

Use dedicated non-production test data where mutation is required.

- application shell / health endpoint load;
- login/current-user succeeds;
- assigned Project is visible; unassigned Project is denied;
- Working Calendar and Activity list load;
- planned/forecast schedule analysis returns;
- current baseline/comparison and Gantt load;
- 2-week or 4-week lookahead loads;
- Daily Site Reports load;
- Equipment register/Project assignment/usage history load;
- Project, WBS and Activity Documents list/download correctly without exposing storage paths;
- Project Engineer Dashboard loads for an assigned Project and is denied for an unassigned user;
- logout revokes the session.

## 4. Migration-specific checks

V0.2 migrations add/strengthen Scheduling, baseline/progress, Site Execution, Equipment, document-target integrity and Reporting permission data.

After migration:

- verify all migration history is applied;
- verify existing V0.1 Project/Document data remains readable;
- verify existing Project document links remain valid;
- verify existing Daily Site Report document links have their Project link (the normal upload path already creates it);
- do not rewrite legacy milestone business dates automatically; the documented V0.2-B milestone migration policy remains authoritative.

## 5. Deployment failure / rollback

If migration or startup fails:

1. stop rollout and prevent further writes where necessary;
2. preserve logs and the failed database/storage state;
3. identify whether migrations committed;
4. if the new schema remains backward-compatible, application rollback may redeploy the previously recorded known-good commit;
5. otherwise restore the verified matching PostgreSQL and document-storage backups;
6. redeploy the application version matching the restored state;
7. rerun migration status and safe smoke checks.

Do not improvise destructive reverse SQL in Production. Prisma migrations remain forward migration history.

## 6. Post-deployment evidence

Record:

- deployed commit
- deployment date/time/operator
- environment identifier
- migration status
- backup identifiers
- smoke result
- any defect/rollback action
- V0.2 UAT/sign-off reference

Production deployment remains prohibited until the approved release/UAT gates and operational target controls are satisfied.
