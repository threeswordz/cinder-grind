## Confirmed visual direction — adjustable, not frozen

1. **Incremental UX redesign, not an ERP rebuild.** Keep the delivered V0.1–V1.0 React/NestJS/Prisma modules, REST APIs, permission behavior and database semantics; refactor their presentation using small reusable components and compatibility adapters.
2. **Desktop layout:** clean English-language example with a dark navy left sidebar, light main workspace, responsive top header, grouped/expandable navigation, clear headings, spacious task cards, scannable tables and concise operational summaries. The exact colors, spacing, labels, card arrangement and metrics can change after real-user feedback.
3. **Top bar:** authenticated user's own name/assigned role label(s) as **read-only**; current authorized Company and Project context; language selector; user profile/settings/logout. Project options and any Company switching must be backed by real approved scope and API—not a decorative/unsafe selector.
4. **Navigation:** Home, My Work, Projects, Procurement (PR, RFQ & Quotations, PO, Goods Receipts, Suppliers), Inventory, Subcontracts, Finance, Cost Control, Reports, and permission-gated Administration (master data, users/roles, Approval Matrix, settings). Group rather than show 25–30 ungrouped developer tabs. Show only authorized modules and retain access to existing released functionality.
5. **Home/My Work:** user-specific summaries, actionable queues, source-linked documents, status and next-action guidance; counts, dates, supplier names and THB amounts must come from scoped source endpoints rather than illustration/mock data. Never place a false approval action in a purchasing user’s queue.
6. **Eight genuine operating role journeys:** Nancy Accounting Manager; Ben General Manager; Khaimook Project Manager/Head of Store; Jai Purchasing Staff; Store Site Store Staff; Foreman Site Foreman; Porn Accounting Staff; Koh HR Staff. Do not hard-code individual user names into permission logic, and do not seed irrelevant names from generated mockups.
7. **Automatic role inheritance on login — NO SWITCH ROLE SECTION.** Administrators assign roles. The backend-authenticated user’s effective `roleCodes` and `permissions` determine a single workspace. Multiple assigned roles combine only that user’s allowed actions. No impersonation, borrowed credentials, "view as" or manual role filter/switcher.
8. **Stage-aware responsive UX:** desktop administrative dashboards, project/store mobile-friendly views; reusable cards, tables, form fieldsets, status styles, breadcrumbs, document attachments and safe deep links to canonical modules.
9. **Localization:** English, Thai and Traditional Chinese for the approved V1.1 surfaces; preserve canonical stored codes and underlying Company currency. Show **THB** only when the source record actually uses THB, with no fabricated FX conversion.
10. **Optional support experience:** an entitled administrator may eventually see a *separate read-only* User Support & Diagnostics screen; this is not a role selector or currently implemented feature. New diagnostic permissions, privacy, audit, API and retention require their own explicit owner authorization.

## Editable improvements after every stage — feedback and change policy

The Product Owner explicitly agreed that the UI is **not final/frozen** and should be improved throughout V1.1-B/C/D/E and in later releases. Apply these distinctions rather than treating every request as the same change:

| Change class | Examples | Gate |
|---|---|---|
| Presentation-only | Color, typography, spacing, icons, card order, table density, responsive layout | Small stage PR, existing permissions, UI regression/accessibility, green CI; do not silently change financial meaning |
| Navigation/workflow UX on approved API | Group menus, add source links, improve form flow/labels, authorized filter, reduce clicks | Scoped issue/PR, verify source semantics/project boundaries, automated tests + human feedback, docs updated |
| New report/counter/aggregation | My Work counts, overdue task lists, read-only summaries | Verify effective Company/Project/permission/step filters and no data-count leak; design/API security review if new endpoints |
| New role authorization or other-user support | Approval eligibility, cross-user diagnostic reads, admin permissions | **Explicit owner-approved security/scope decision**, redaction/audit tests, DEC-022 stable-candidate review, cannot imply business approval |
| New business rules/data model | Maker-checker exception, PO/GR stock posting, BOQ revisions, SC variations, tax, payroll, numbering/finance | **Prior Product Owner Change Control**, revised scope/AC/BR, forward-only migration when applicable, CI/security/UAT |
| Post-release enhancement | Later visual refresh or independent module workflow | Separate approved scoped stage/release; no silent reopening of already accepted release history |

**Feedback loop for each approved implementation stage:**
1. Re-fetch live GitHub and stage authority; capture a short user scenario + before/after requirement (screenshots can be attached when available).
2. Classify the change and scope, and check the 54-item traceability/role matrix and existing backend rights; raise a Change Control decision before any new rule.
3. Change the **smallest reusable component or source-owned panel**, not the entire app or schema; keep backward compatibility/legacy navigation during transition.
4. Test browser desktop/mobile, role/Company/Project denials, original backend behavior, locale and THB/currency correctness. Use DEC-022 stable-candidate review where required.
5. Merge only after applicable exact-head/PR checks, then post-merge exact-main CI; update `docs/CURRENT-STATE.md`, `docs/DEVELOPMENT-ROADMAP.md`, stage documentation and UAT evidence *as authorized for that active release*.
6. Have real users validate workflow usability and the Product Owner explicitly accept applicable human-only UAT/release decisions. Carry incomplete enhancements to a tracked backlog and never call them finished.

## Proposed stage checkpoints (subject to formal release entry approval)

- **V1.1-A**: Approve scope, eight-role matrix, 54-workflow gaps, canonical API/security/test baselines and this non-frozen UX direction. No UI application code.
- **V1.1-B**: Build reusable shell and permissions-based navigation/Home/My Work **around existing released panels**, starting with purchasing. Review layout and mobile/locale usability.
- **V1.1-C**: Link authorized purchase, inventory, subcontract and finance transactions end-to-end. Refine task tables/form journeys with Store Site, Jai, Khaimook, Ben, Porn and Nancy; never change approvals by visual styling.
- **V1.1-D**: Polish/refine accessibility, performance and security. Implement *only* separately authorized business-rule/diagnostic changes; otherwise keep them deferred.
- **V1.1-E**: Demonstrate eight-persona end-to-end UAT, responsive/localized views, negative access tests and no V0.1–V1.0 regression; Product Owner remains sole business acceptor.

## Scope/approval boundary

These are **documented design preferences and a proposed improvement process**, not consent to merge PR #212, start V1.1 coding, change high-risk backend rules, or waive CI. The Product Owner must approve the full bounded V1.1 entry package and required decisions/deferrals separately. The draft PR/Issue is the durable proposal record until an authorized entry closure merges to `main`.

**Recommended technical implementation:** configurable styling and reusable shell components; preserve source-owned data/mutations, accessible responsive layouts, three-language message catalogs and a permission-safe derived My Work model. The frontend may be redesigned iteratively without a drastic backend rewrite.
